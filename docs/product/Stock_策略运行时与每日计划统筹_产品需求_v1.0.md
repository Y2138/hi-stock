## 一、双角色最终结论

### 1.1 产品负责人结论

当前系统已经拥有多类策略、信号工具和独立任务，但用户实际关心的是一条连续链路：

```text
当前策略是什么
→ 今天是否出现入场信号
→ 哪些标的应进入或退出关注池
→ 已持仓标的是按哪个策略管理
→ 今天是否出现减仓或退出信号
→ 每日计划是否完整覆盖了全部持仓和全部有效策略
```

现状将这些能力拆散在策略正文、任务提示词、工具名称和持仓的 `entry_signal_type` 中，导致用户无法在一个页面确认关联关系，也无法判断每日计划是否遗漏某个策略。

产品上必须形成以下确定性体验：

1. 每个可执行策略都有明确的入场评估器、出场评估器、关注池规则和可选兜底策略。
2. 每笔持仓都能追溯到唯一的当前管理策略；无法归属时必须显式显示“待归因”，不得静默套用规则。
3. 入场评估结果自动维护该策略在关注池中的来源条目，关注池来源按策略而不是按任务去重。
4. 每日计划自动覆盖所有应参与的策略和全部持仓，不要求用户或 Agent 手工挑选工具。
5. 分批止盈与移动止损归入独立的“兜底出场策略”，页面必须明确展示是否启用、何时生效以及本次是否实际采用。
6. 专项 Agent 任务继续保留，但任务只负责触发和解释，不再拥有一套独立的策略计算事实。
7. 同一策略、同一目标日、同一输入版本只执行一次评估；多个任务复用同一结构化结果。
8. 产品不提供任意策略—任务多对多编辑器，避免关系失控、重复执行和难以审计。

### 1.2 资深架构师结论

系统应从“任务调用工具”升级为“策略运行时驱动”：

```text
策略定义
├── 当前策略文档
├── 入场评估器
├── 出场评估器
├── 关注池投影规则
├── 兜底策略
└── 每日计划参与范围

Agent 任务
└── 只绑定零个或一个策略，并声明任务角色

每日计划
└── 作为组合级聚合器，自动发现应执行的策略与持仓，不建立逐条多对多绑定
```

核心技术结论：

1. 工具是 Agent 边界适配器，不是业务逻辑本体；每日计划不应在工具内部调用其他工具。
2. 入场与出场逻辑必须抽成可注册、可版本化的服务端评估器；专项工具和每日计划共同复用评估器。
3. 数据库只保存经过代码白名单校验的评估器编码，不保存模块路径、脚本、SQL 或可执行代码。
4. 任务和策略采用“任务至多属于一个策略、策略可拥有多个不同用途任务”的一对多关系；每日计划是特殊聚合任务，不与所有策略建立多对多行。
5. 使用结构化评估运行表和输入指纹完成幂等、复用、审计和失败隔离。
6. 关注池条目的业务所有者是策略，不是触发任务；任务编码只保留为最近一次执行来源。
7. 兜底策略必须通过显式配置参与，不允许因主评估器技术失败而被系统无声替换。
8. 当前同一标的加仓会覆盖整笔持仓信号类型，首期必须收口为“一只标的的当前持仓只允许一个管理策略”。

## 二、背景与问题

### 2.1 当前能力

系统当前已经具备：

- PostgreSQL 当前策略文档；
- 波段、两年结构反转、打板、价值错杀、商品库存等垂直评估能力；
- 右侧、试盘、旧左侧等存量评估逻辑；
- 独立 Agent 定时任务；
- 单一关注池及多来源关注条目；
- 持仓买入信号类型；
- 每日计划结构化持仓预案；
- 任务运行、审计、确认和通知能力。

### 2.2 当前问题

#### 2.2.1 策略关联不完整

`strategy_document.job_code` 只能表达任务读取哪篇策略文档，不能表达：

- 策略使用哪个入场评估器；
- 策略使用哪个出场评估器；
- 入场结果如何进入关注池；
- 持仓应由哪个策略管理；
- 是否启用兜底出场策略；
- 是否应被每日计划统筹。

#### 2.2.2 每日计划承担了过多策略逻辑

当前每日计划上下文同时计算市场状态、右侧、试盘、波段持仓、旧左侧持仓和短线兜底触发位。策略新增或变化时，需要同步修改提示词、工具白名单、完成门禁和大型条件分支。

#### 2.2.3 关注来源按任务识别

现有关注条目以 `source_job` 区分来源。当专项任务和每日计划都执行同一策略时，可能出现：

- 同一策略重复写入关注；
- 不同任务互相清理或保留错误条目；
- 用户看到的是任务来源，无法直接理解策略来源；
- 任务改名或拆分后，关注归属失真。

#### 2.2.4 持仓只有信号类型

`entry_signal_type` 是固定枚举，不是完整策略身份。它无法关联当前策略文档、评估器版本、关注来源或具体入场信号。

#### 2.2.5 同标的加仓会覆盖管理口径

同一标的已有持仓后再次买入，当前实现会用最新买入的信号类型覆盖整笔持仓的管理口径。若两次买入来源不同，原仓位会被错误地套用新策略出场规则。

#### 2.2.6 任务工具关系重复维护

任务工具范围、任务提示词和完成门禁分别维护工具清单。新增策略时存在遗漏、错配和重复执行风险。

## 三、产品目标与非目标

### 3.1 产品目标

1. 建立策略、入场评估器、出场评估器、关注池、持仓和 Agent 任务之间的确定性关联。
2. 每日计划能够自动发现全部应评估策略，并根据持仓策略归属执行正确的出场评估。
3. 入场评估器与关注池建立完整集合对账关系，不依赖具体触发任务。
4. 将既有分批止盈和移动止损沉淀为可复用的兜底出场策略。
5. 避免策略—任务任意多对多配置，降低维护成本。
6. 同一评估结果可被每日计划、专项任务和交互查询复用，避免重复执行。
7. 前端能够直观展示策略关联、覆盖情况、关注来源、持仓归属、兜底策略和评估缺口。
8. 保持 PostgreSQL 为运行时唯一事实源，保持领域服务写入边界和 Agent 安全约束。

### 3.2 非目标

1. 不实现自动下单、自动成交或券商连接。
2. 不允许 Agent 自主创建、修改或发布策略。
3. 不在首期实现同一标的多个策略子仓位并存。
4. 不建设任意拖拽式工作流编排器。
5. 不允许用户在前端填写任意工具名、代码模块、SQL 或脚本。
6. 不强制所有研究任务转成持仓策略；纯研究和数据同步任务可以保持无策略归属。
7. 不恢复系统内回测执行能力。
8. 不以兜底策略掩盖主策略评估器的数据缺口或技术失败。

## 四、核心概念

### 4.1 策略定义

“策略定义”是运行时稳定身份，不等同于策略文档。它负责关联文档与执行能力。

每个策略定义至少包含：

- 稳定编码；
- 名称；
- 类型；
- 当前策略文档；
- 状态；
- 是否允许新开仓；
- 入场评估器；
- 出场评估器；
- 关注池投影规则；
- 可选兜底策略；
- 每日计划参与范围；
- 当前运行版本。

### 4.2 策略类型

| 类型 | 说明 | 示例 |
|---|---|---|
| `position` | 可形成持仓归属，至少具备入场或出场能力 | 波段、两年结构反转、旧左侧 |
| `attention` | 只形成关注条目，不直接成为持仓管理策略 | 板块机会筛选 |
| `observation` | 只形成观察结果，不自动写关注或持仓 | 打板观察、研究性商品信号 |
| `fallback_exit` | 不产生入场，只提供通用出场保护 | 分批止盈与移动止损 |
| `portfolio_overlay` | 形成组合级风险或暴露判断 | 商品库存防守、组合风险闸门 |

首期允许策略只实现部分能力；缺少的能力必须在页面中明确展示，不得自动推断。

### 4.3 入场评估器

入场评估器按策略规则和目标日数据输出：

- 正式信号；
- 接近候选；
- 筛除项汇总；
- 数据覆盖；
- 数据缺口；
- 关注池建议状态；
- 触发条件与失效条件；
- 评估器版本和输入指纹。

### 4.4 出场评估器

出场评估器接收属于该策略的一组当前持仓，输出：

- 继续持有；
- 观察；
- 减仓；
- 全部退出；
- 价格触发位；
- 时间触发条件；
- 保护位；
- 数据缺口；
- 主策略动作优先级。

### 4.5 兜底出场策略

兜底出场策略是一个正式策略定义：

```text
code = portfolio_fallback_exit
类型 = fallback_exit
入场评估器 = 无
出场评估器 = fallback_exit_v1
```

其现行职责为承接既有的通用持仓保护规则，包括：

- 冷却期安全止损；
- 按股性选择的技术止损；
- 第一档分批止盈；
- 第二档分批止盈；
- 盈利后逐级抬高保护位；
- MA5 等技术保护参考；
- 移动止损只上移、不向下放宽。

右侧结构崩坏、MACD 弱化、持有时间兜底等策略特有判断不属于通用兜底策略，应保留在对应策略的专属出场评估器中。

### 4.6 评估运行

评估运行是一次可复用、可审计的结构化执行，身份由以下内容决定：

```text
策略编码
+ 阶段（entry/exit/overlay）
+ 目标日
+ 评估器编码与版本
+ 输入指纹
```

每日计划、专项任务和交互查询均消费评估运行，不分别复制计算结果。

### 4.7 策略关注条目

策略关注条目表示某策略在某标的上的当前关注状态。其身份为：

```text
instrument_id + strategy_code
```

任务只是触发来源，不参与唯一性判断。

```text
        └── 写入每日计划结构化预案
```

## 六、策略与任务关系

### 6.1 关系原则

不建立允许任意编辑的策略—任务多对多关系。

采用以下模型：

1. 一个普通 Agent 任务最多关联一个策略；
2. 一个策略可以按不同用途拥有多个任务；
3. 同一策略、同一任务用途最多一个启用任务；
4. 每日计划是组合聚合任务，不直接关联具体策略；
5. 每日计划通过策略配置和持仓事实自动发现策略；
6. 跨域集合竞价任务 `auction_cross_scope` 不绑定任何单一策略，独立复核每条有效关注来源、盘中涨停梯队和每日计划打板机会；持仓竞价复核已下线，任务改为全局单次执行，打板评分仍由每日计划生成；
7. 数据同步任务、通知任务和纯研究任务可以不关联策略。

### 6.2 Agent 任务角色

| 角色 | 是否关联策略 | 职责 |
|---|---:|---|
| `strategy_entry_report` | 必须且仅一个 | 输出某策略入场信号专项报告 |
| `strategy_exit_report` | 必须且仅一个 | 输出某策略或组合的专项出场评估报告 |
| `strategy_confirmation` | 必须且仅一个 | 单策略候选的专属确认（不用于集合竞价跨域任务） |
| `auction_cross_scope` | 不关联单一策略 | 按目标日最终竞价，分别复核全部持仓、每条策略/人工关注来源和打板机会 |
| `portfolio_aggregator` | 不关联单一策略 | 每日计划，自动聚合策略和持仓 |
| `data_pipeline` | 不要求 | 同步行情、目录、成分、财务和商品数据 |
| `research_report` | 可选 | 输出研究结论，不直接维护持仓策略事实 |

### 6.3 防重复执行

任务不直接拥有评估结果。所有任务通过评估服务执行：

```text
ensureStrategyEvaluation(strategy, phase, targetDate)
```

规则：

1. 已存在相同输入指纹的成功运行：直接复用；
2. 已存在运行中记录：等待或返回运行中，不创建第二条；
3. 已存在部分或失败记录且输入未变化：按重试规则执行，不并发重复执行；
4. 输入数据推进后指纹变化：允许创建新运行；
5. 专项任务必须在结果中标明“本次新执行”或“复用运行”；
6. 每日计划只消费目标日当前有效运行；
7. 数据滞后时不得用前一日成功运行冒充目标日结论。

### 6.4 任务完成门禁

完成门禁按任务角色生成，不再为每个策略手工维护工具名数组。

- 单策略任务：必须读取组合总策略、该策略文档和该策略评估运行；
- 每日计划：必须读取组合总策略、全部相关策略文档、组合评估结果并完成结构化计划写入；
- 关注型策略任务：成功评估后必须完成该策略的关注集合对账；
- 数据部分或不可用时：必须报告缺口，不得伪造完成。

## 七、入场评估与关注池关联

### 7.1 关注池投影配置

每个有入场或关注能力的策略声明 `attention_policy`：

| 配置 | 行为 |
|---|---|
| `none` | 不写入关注池 |
| `qualified_only` | 仅正式信号写入“已符合” |
| `qualified_and_approaching` | 正式信号写“已符合”，接近候选写“即将符合” |
| `manual_review` | 工具只输出候选，须经真实用户确认后进入人工关注 |

### 7.2 关注条目归属

策略条目以 `strategy_code` 为业务来源，保留以下审计字段：

- 最近评估运行；
- 最近触发任务；
- 目标日与数据日；
- 评估器版本；
- 信号状态；
- 关注理由；
- 尚缺条件；
- 生效和失效日期；
- 是否过期或数据滞后。

人工关注保持独立，不关联策略，不被策略对账删除。

### 7.3 完整集合对账

#### 成功运行

对该策略执行完整集合对账：

1. 正式信号和接近候选新增或更新；
2. 本轮未出现的旧策略关注条目结束；
3. 已持仓标的不写入策略关注；
4. 买入成交后消费对应策略关注条目；
5. 其他策略和人工关注不受影响。

#### 部分运行

只更新已完成评估的标的；未完成范围的旧条目保留并标记“待复核”，不得按缺席删除。

#### 不可用或失败

不改变策略关注集合，只记录本轮缺口和最后成功数据日。

### 7.4 同标的多策略关注

同一标的可以同时被多个策略关注，但前端只展示一行标的，展开后展示多个策略来源。

示例：

```text
600000.SH
├── 波段策略：即将符合，缺 RSI14<40
├── 两年结构反转：已符合
└── 人工关注：长期跟踪
```

## 八、持仓策略归属

### 8.1 首期业务约束

同一标的当前有效持仓只能由一个策略管理。

规则：

1. 首次买入必须填写 `strategy_code`；
2. 正式系统信号买入应关联具体 `strategy_signal_id`；
3. 自主决策买入关联 `discretionary` 策略；
4. 已有持仓再次买入时，策略必须与当前持仓一致；
5. 不同策略加仓必须被拒绝，并提示用户先确认是否整体变更管理策略；
6. 整体变更策略属于事实修正或真实决策，必须记录原因和确认；
7. 卖出事件继承当前持仓策略，不允许填写另一策略；
8. 清仓后再次建仓可以选择新策略。

### 8.2 持仓运行字段

当前持仓增加：

- `strategy_code`；
- `strategy_runtime_version`；
- `entry_signal_id`；
- `fallback_strategy_code`；
- `exit_policy_mode`；
- 最近成功出场评估运行；
- 最近评估状态。

成交事件同步保存上述归因字段。原有全局策略快照哈希继续保留，用于审计当时系统整体状态。

### 8.3 存量回填

| 现有 `entry_signal_type` | 新策略编码 |
|---|---|
| `swing` | `swing` |
| `right_side` | `legacy_right_side` |
| `trial_start` | `legacy_trial_start` |
| `left_reversal` | `legacy_left_reversal` |
| `two_year_reversal` | `two_year_reversal` |
| `limit_up` | `limit_up` |
| `discretionary` | `discretionary` |
| 空值或无法确认 | `unassigned`，必须人工归因 |

旧右侧、旧试盘和旧左侧策略状态设为“仅退出”，不允许产生新开仓。

## 九、兜底出场策略

### 9.1 出场模式

每个持仓策略必须声明以下一种模式：

| 模式 | 行为 |
|---|---|
| `dedicated` | 只使用主策略专属出场评估器 |
| `fallback_only` | 只使用兜底出场策略 |
| `dedicated_plus_fallback` | 同时评估主策略和兜底策略，按固定优先级合并 |

### 9.2 推荐初始映射

| 策略 | 出场模式 | 说明 |
|---|---|---|
| 波段 | `dedicated` | 使用箱体、观察期、止损、到期和突破后移动保护 |
| 两年结构反转 | `dedicated` | 使用信号日低点、MA20 修复和 ATR 移动止损 |
| 旧左侧反转 | `dedicated` | 使用旧左侧止损、6%/16% 分批与 10 日到期 |
| 旧右侧主升 | `dedicated_plus_fallback` | 主策略负责结构崩坏，兜底负责分批止盈与移动止损 |
| 旧试盘启动 | `fallback_only` | 不再使用试盘形态作为出场规则 |
| 自主决策 | `fallback_only` | 没有专属策略时使用明确的通用保护规则 |
| 打板 | 首期按现行最终规则配置 | 不得无规则回退 |

### 9.3 合并优先级

`dedicated_plus_fallback` 模式保留主策略和兜底策略的全部触发条件，同时生成一个 `effective_action`：

```text
硬止损或强制全退
> 主策略明确全退
> 时间到期全退
> 主策略减仓
> 兜底分批止盈
> 抬高保护位
> 继续持有/观察
```

页面必须同时展示：

- 主策略动作；
- 兜底策略动作；
- 最终有效动作；
- 最终动作采用哪条规则；
- 是否存在评估缺口。

### 9.4 失败处理

1. `fallback_only`：兜底评估器失败时，该持仓为未覆盖；
2. `dedicated`：主评估器失败时，不自动套用兜底；
3. `dedicated_plus_fallback`：两个评估器独立报告状态；任一成功结果可以展示，但失败不得被隐藏；
4. 不允许仅因为工具调用失败而临时改变出场模式；
5. 评估器不存在或版本不匹配时，每日计划必须标记阻断性缺口。

## 十、每日计划统筹流程

### 10.1 每日计划输入

1. 目标日和实际数据日；
2. 当前组合总策略；
3. 当前启用的策略定义；
4. 当前持仓及策略归属；
5. 当日市场状态和风险门禁；
6. 目标日当前有效评估运行；
7. 最近一份未失效计划动作；
8. 关注池当前策略来源状态。

### 10.2 策略自动发现

每日计划不维护策略名单，按以下规则发现：

#### 入场范围

```text
strategy_definition.status = active
AND allow_new_entry = true
AND daily_plan_scope 包含 entry
```

#### 出场范围

```text
当前持仓实际出现的 strategy_code
+ 对应显式 fallback_strategy_code
```

即使策略已经设置为“仅退出”，只要仍有持仓，每日计划仍必须执行其出场评估。

#### 组合上下文范围

```text
daily_plan_scope 包含 context 的 portfolio_overlay 策略
```

### 10.3 执行步骤

1. 锁定目标日、策略状态哈希和策略运行版本；
2. 读取全部持仓并校验策略归属；
3. 加载需要执行的唯一评估器集合；
4. 为入场策略确保目标日入场评估运行；
5. 按策略批量执行持仓出场评估；
6. 按持仓配置执行兜底策略；
7. 生成策略关注池对账变更；
8. 合并组合风险门禁；
9. 生成每笔持仓的主策略、兜底和最终动作；
10. 生成入场信号、接近候选和关注变更；
11. 写入结构化每日计划；
12. 保存覆盖统计、复用情况和缺口。

### 10.4 结构化输出

每日计划结果增加：

```text
strategy_coverage
entry_evaluations
attention_changes
position_evaluations
fallback_evaluations
evaluation_runs
gaps
```

每笔持仓预案至少包含：

- `strategy_code`；
- `strategy_name`；
- `strategy_runtime_version`；
- `primary_evaluator_code`；
- `fallback_strategy_code`；
- `exit_policy_mode`；
- `primary_action`；
- `fallback_action`；
- `effective_action`；
- `trigger_kind` 与价格区间；
- `evaluation_status`；
- `evaluation_run_id`；
- `data_date`；
- `missing_items`。

### 10.5 覆盖门禁

每日计划完成前必须检查：

- 持仓总数；
- 已绑定策略持仓数；
- 已完成主策略评估数；
- 应执行兜底持仓数；
- 已完成兜底评估数；
- 未绑定持仓数；
- 缺少评估器持仓数；
- 入场策略应评估数与完成数；
- 关注集合对账完成数；
- 数据滞后策略数。

存在未绑定持仓、缺少出场评估器或阻断性数据缺口时，计划状态为 `partial`，不得显示为完整覆盖。

## 十一、服务端设计要求

### 11.1 策略定义表

建议新增 `strategy_definition`：

```text

status                       active | exit_only | paused | retired
allow_new_entry              boolean not null

attention_policy             none | qualified_only | qualified_and_approaching | manual_review
```

约束：

1. `allow_new_entry=true` 必须存在入场评估器；

3. `fallback_exit` 策略不得配置入场评估器；

- `portfolio_aggregator` 不允许填写 `strategy_code`；
- 同一策略同一 `agent_role` 最多一个启用任务；

评估器直接调用领域 service；Agent 工具和每日计划编排器只是适配层。

### 11.9 Agent 工具

新增两个统一工具：

#### `strategy_evaluation_query`

用于单策略专项任务和交互查询：

```text
strategy_code
phase
目标日
```

任务会话中 `strategy_code` 由服务端任务范围固定，Agent 不得改为其他策略。

#### `daily_plan_strategy_query`

用于每日计划：

- 自动读取持仓策略；
- 自动发现入场策略；
- 批量执行或复用评估运行；
- 返回统一结构化结果；
- 不接受 Agent 自行指定工具名或任意策略列表。

现有垂直工具在迁移期继续保留，内部改为调用同一评估器；完成迁移后根据交互价值决定保留为便捷别名或退役。

现有 `position_actions` 和 `opportunities` 保持兼容，逐步增加策略归属字段。

## 十四、安全与权限

1. 策略正文继续只读，由迁移和人工确认后的代码变更维护；
2. 评估器编码只允许代码注册表白名单；
3. Agent 不得写入或修改策略绑定；
4. Agent 不得通过数据库工具绕过领域服务；
5. 持仓策略修正属于业务写入，必须经过确认；
6. 关注池自动对账只能修改同一策略自己的条目；
7. 每日计划不能修改持仓、成交或策略；
8. 兜底策略只能按持仓已固化配置执行；
9. 技术失败不得静默切换策略；
10. 所有评估运行、复用、失败和对账均写入审计事实；
11. API Key、账户、持仓、信号运行和关注结果属于本机运行数据，不进入 Git 固定资产；
12. 策略定义、任务定义和评估器绑定属于可移植固定资产，需纳入导出、恢复和校验白名单。

## 十六、异常处理

| 场景 | 系统行为 |
|---|---|
| 持仓无策略 | 标记待归因，计划 `partial`，不静默套用兜底 |
| 策略无出场评估器且无兜底 | 阻断性缺口 |
| 入场评估器数据不足 | 不产生正式信号；部分结果按规则维护关注 |
| 入场评估器失败 | 不改变该策略关注集合 |
| 主策略失败、兜底成功 | 仅在持仓已配置兜底时展示兜底动作，并明确主策略缺口 |
| 兜底失败、主策略成功 | 展示主策略动作，计划标记兜底缺口 |
| 相同评估并发请求 | 只执行一次，其余复用或等待 |
| 输入数据更新 | 生成新输入指纹和新运行 |
| 专项任务晚于每日计划执行 | 复用每日计划已生成的同日评估运行 |
| 专项任务早于每日计划执行 | 每日计划复用专项任务评估运行 |
| 同标的不同策略加仓 | 首期拒绝并要求确认管理策略 |
| 策略已停止新开仓但仍有持仓 | 继续执行出场评估直到清零 |
| 策略文档与运行版本不匹配 | 阻断对应策略评估并报警 |

## 十八、验收标准

### 18.1 策略关联

1. 每个启用策略都能查看当前文档、评估器、关注规则、兜底和每日计划范围；
2. 数据库引用不存在的评估器时，服务启动或迁移校验失败；
3. 旧右侧、试盘和旧左侧不能产生新开仓；
4. 仅退出策略在持仓清零前持续执行出场评估。

### 18.2 关注池

1. 同一标的同一策略最多一条自动关注；
2. 两个任务请求同一策略评估不会产生两条关注；
3. 不同策略可以同时关注同一标的；
4. 人工关注不被策略对账清除；
5. 成功运行执行完整对账；
6. 部分运行不删除未覆盖条目；
7. 失败运行不修改关注集合。

### 18.3 持仓和出场

1. 所有新增买入都必须有策略归属；
2. 同标的不同策略加仓被拒绝；
3. 每笔持仓能唯一找到主出场评估器或显式兜底；
4. 分批止盈和移动止损显示为兜底策略结果；
5. 主策略与兜底动作均可追溯；
6. 缺少评估器不得回退到未知规则；
7. 存量持仓迁移后，相同输入的触发位与重构前一致。

### 18.4 任务和幂等

1. 普通策略任务最多关联一个策略；
2. 每日计划不维护策略多选关系；
3. 同策略、阶段、目标日、版本和输入指纹只执行一次；
4. 专项任务和每日计划可以双向复用结果；
5. 任务详情显示复用来源；
6. 完成门禁由任务角色和策略能力确定。

### 18.5 每日计划

1. 自动发现全部应参与入场评估的策略；
2. 自动覆盖全部当前持仓策略；
3. 自动执行配置的兜底策略；
4. 显示持仓、策略、关注和数据覆盖统计；
5. 未绑定持仓或缺失评估器时状态为 `partial`；
6. Agent 不需要逐个加载策略工具；
7. 输出动作与结构化预案一致。

### 18.6 前端

1. 策略中心能够查看完整运行关系；
2. 关注池按标的聚合策略来源；
3. 持仓页显示主策略、兜底策略和最终动作；
4. 每日计划显示覆盖摘要和动作来源；
5. 任务中心不提供任意多对多策略编辑；
6. 仪表盘能够提示待归因和评估缺口；
7. 桌面宽度和移动宽度下均能识别关键信息，不依赖横向超宽表格完成核心操作。

## 二十一、最终产品边界

本需求完成后，系统的职责关系固定为：

```text
策略文档：保存当前最终规则
策略定义：声明运行能力和关联
评估器：执行入场、出场和组合判断
评估运行：提供结构化、可复用的唯一事实
关注池：承接按策略归属的入场候选
持仓：保存唯一当前管理策略
兜底策略：提供显式通用出场保护
专项任务：触发并解释单一策略评估
每日计划：自动聚合全部相关策略和持仓
Agent：调用受控工具、解释结果、写入受控业务对象
用户：决定交易、策略归因和任何需要确认的变更
```

新增策略的标准接入动作收敛为：

1. 增加当前策略文档；
2. 注册入场和/或出场评估器；
3. 增加策略定义；
4. 配置关注规则、兜底和每日计划范围；
5. 可选增加一个或多个单策略专项任务；
6. 通过统一评估运行、关注投影和每日计划编排自动接入系统。

新增策略不再要求修改每日计划的策略名单、逐策略工具清单或持仓条件分支。

## 集合竞价跨域研判的最终边界

- 每日计划继续按当前《打板策略》执行打板评分和机会生成，不把竞价当作打板入场评估器。
- 工作日竞价 Agent 任务为独立 `auction_cross_scope`，不关联单一策略，取消持仓复核后按全局单次执行；关注、盘中梯队和打板三类目标共享同一次最终竞价取数，但分别采用不同的评价规则。
- 持仓竞价复核已下线：竞价任务不再读取或改判持仓结论，持仓预案仍由每日计划维护。
- 关注池按每个有效来源条目分别核查原策略缺口；同标的多策略关注逐条输出确认、等待、放弃或数据不足，不把竞价单项说成策略正式信号。
- 打板机会只使用《打板策略》专属一字延续、换手晋级、分歧承接和放弃/数据不足口径；竞价通过是用户自主决策候选，不是自动成交。
- `auction_context_query` 一次返回关注、盘中梯队和打板机会目标及稳定目标键；`auction_assessment_write` 同事务按关注/梯队全集对账并写入草稿，任务成功后才激活。任一目标的真实竞价数据不就绪只能标记不可用。
- 关注的已激活竞价研判从 `/api/auction/latest` 读取；历史持仓结论不再返回，打板机会仍从每日计划结构化预案及其竞价复核读取。

## 情景与做 T 预案结构化（每日计划 v2）

- 每日计划结论文档采用固定骨架（市场与板块观察 / 逐只持仓预案 / 对立板块盯盘 / 数据缺口 / 结论摘要），每只持仓以「服务端预案段落 + 情景四列表格」呈现，消除同模型多次生成的格式漂移。
- 每日计划统筹查询由服务端一并返回每只持仓的关键点位事实（MA5/MA10/MA20、近10/20日高低、前日高低、次日涨跌停价）、所属一级行业当日表现与全市场板块强弱排行；对立板块盯盘不再因工具未开放而缺席。
- 情景预案（冲高回落/开盘下砸/全天宽幅波动/强势延续/弱势破位 × 可观测触发/应对/失效条件）与做 T 区间经 `daily_plan_scenario_write` 结构化落库，任务完成门禁核对其覆盖全部持仓。
- 情景与做 T 只依据关键点位、市场与板块当日表现，不依赖持仓初始策略归因；不以冷却期、止盈核对期等状态为由拒绝给出点位，硬性退出触发只决定优先级。做 T 默认写明低吸区、兑现区与确认/取消条件，仅流动性极端可显式说明后不设。
- 持仓页以持仓明细为主体：执行预案不再单独成块，改为明细表内「查看预案」按钮，点击打开概览、关键点位、做 T 预案、情景矩阵与盯防风险抽屉；明细表移除盘中加减仓列；盘中加减仓折叠为一行摘要（触发计数、观察状态与采样时间），按需展开价位明细；竞价持仓复核模块下线。

## 每日计划移至盘前并接入盘前消息面（每日计划 v2.1）

- 每日计划任务从收盘后 18:15 移至交易日 09:05 盘前执行，位于 08:45 盘前消息面探查之后、09:26 集合竞价跨域研判之前；预案覆盖即将开盘的交易时段。持仓页不再单列预案入口，执行预案并入持仓明细表按行打开。
