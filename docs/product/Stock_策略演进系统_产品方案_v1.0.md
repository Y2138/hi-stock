## 一、已确认启动决策

| 编号 | 真实用户决定 | 落地方式 |
|------|--------------|----------|
| E1 | 数据库升格为事实源，Markdown 逐步降级为导出/展示层 | 一期仅新结构化数据（任务运行、回测登记）原生入库；既有 Markdown 事实源按模块逐个移交，移交完成前 Markdown 仍是事实源 |
| E2 | 数据库选型 PostgreSQL | 本地 docker-compose 实例，连接串走 gitignored 的 `.env.local` |
| E3 | 服务端技术栈 Node/TypeScript | 与仓库现有构建器、vitest/playwright 测试同栈 |
| E4 | 分阶段实施，一期先管任务 + 回测 | 一期：数据库骨架、定时任务运行记录、回测方案/代码/结果登记；二期：标的池、持仓、行情数据结构化；三期：策略版本管理与完整界面 |

## 二、用户问题与系统定位

目标用户仍为同一 A 股个人投资者。痛点是：策略、标的池、持仓、回测、计划、任务分散在 Markdown 与脚本输出中，演进过程（哪次回测支持哪条参数、哪次任务产出了什么、事实源何时变化）无法追溯、无法查询、无法对比。

本系统把策略演进过程工程化：用 PostgreSQL 维护结构化事实，用服务端 API 提供查询，用页面呈现台账，用摄取脚本把既有文件登记进库。它不是交易执行系统，不生成计划，不替代策略文件中的参数定义。

## 三、六大模块与分阶段范围

| 模块 | 内容 | 一期 | 二期 | 三期 |
|------|------|------|------|------|
| 策略文件管理 | 策略文档版本、diff、演进时间线 | 不实施 | 不实施 | 实施 |
| 标的池管理 | 标的、角色、分级、生效区间版本化 | 不实施 | 实施 | 完善 |
| 标的/板块数据 | 行情 CSV 登记与结构化 | 只登记元数据（路径、哈希、覆盖范围） | K 线入库 | 完善 |
| 持仓池 | 持仓快照、执行位历史 | 不实施 | 实施 | 完善 |
| 回测方案/代码/结果 | 运行登记、配置快照、输入清单、产物哈希、正式锚点 | **实施** | 完善 | 完善 |
| 定时任务与结果 | 任务定义、运行记录、产物与数据缺口 | **实施** | 完善 | 完善 |

## 四、一期目标与非目标

### 4.1 目标

- 三个定时任务（每日交易计划、周中短线检查、每周评分）有任务定义记录，每次运行可登记目标日、触发方式、状态、步骤日志、产物和数据缺口。
- 每次回测运行可登记引擎路径、Git 提交、配置快照、输入文件清单（含哈希）、产物、报告链接与摘要指标；同一时刻只有一个"正式锚点"。
- 既有事实可追溯：3 份任务模板、当前正式回测及 `支撑/results/` 历史报告、`支撑/data/` 行情 CSV 全部登记入 `dataset`，携带路径与 SHA-256。
- 页面上能查看任务运行台账和回测台账，正式锚点置顶。
- 摄取全程只读 `支撑/` 与根目录事实文件；一期不修改、不搬迁任何既有事实源。

### 4.2 非目标（一期）

- 不搬迁策略/标的池/持仓/计划 Markdown 的事实源地位。
- 不做实时行情、交易事实写入、计划自动生成、标的池维护界面。
- 不做用户账号、权限、多设备、远程部署。
- 不引入 ORM、Web 框架、前端框架；不从历史报告正文猜测补录指标数字。

## 五、一期功能契约

### 5.1 任务运行台账

| 项目 | 定义 |
|------|------|
| 任务定义 | code（`daily_plan`/`midweek_check`/`weekly_review`）、名称、模板路径与哈希、cron、启用状态；由种子脚本从 `定时任务/*.md` 登记 |
| 运行记录 | 目标交易日、触发方式（cron/manual）、状态（running/success/failed/partial）、起止时间、步骤日志、产物清单（计划文件、更新过的持仓与流水、数据更新摘要）、数据缺口、总结 |
| 唯一性 | 同一任务同一目标日只允许一条运行记录，防重复登记 |
| 写入方式 | 运行开始/结束通过 CLI（`scripts/record-task-run.mjs`）调 API 记录；不改 agent 现有任务执行流程 |

### 5.2 回测台账

| 项目 | 定义 |
|------|------|
| 运行登记 | 名称、类型（formal/research）、引擎路径、Git 提交、配置快照（JSONB）、输入清单（路径+哈希）、输出目录、报告路径、状态、起止时间、摘要指标、备注 |
| 正式锚点 | `kind='formal'` 且 `status='active'` 的运行全局唯一；激活新锚点在事务内降级旧锚点 |
| 产物关联 | 输出目录文件与报告文件先入 `dataset`，再通过 `backtest_artifact` 关联，角色分 output/report/input |
| 历史登记 | `支撑/results/` 既有报告按文件名解析版本与日期，登记为 `archived`；缺失指标留空，不编造 |
| 写入方式 | `scripts/register-backtest.mjs` CLI；日常由 agent 在回测完成后调用 |

### 5.3 数据集登记

| 项目 | 定义 |
|------|------|
| 范围 | `支撑/data/` 日线/30分钟/期货 CSV、回测产物、报告 Markdown、任务模板 |
| 字段 | 受控标识、相对路径、SHA-256、类型、覆盖起止日、行数、登记时间 |
| 语义 | 只证明本地可追溯性，不声称上游来源已核实（沿用纯前端 MVP 的证据分组原则） |

### 5.4 页面

一期两个新视图，由本地服务托管、从 API 取数：

- **任务运行**：任务定义列表 + 每个任务的运行记录（状态、目标日、产物、缺口）。
- **回测台账**：运行列表（正式锚点置顶）、详情含配置快照、输入清单、产物哈希、报告链接。

旧纯前端视图与静态构建流程保持不动，新旧视图互不干扰。

## 六、移交原则（E1 的执行规则）

1. 模块未移交前，对应 Markdown 文件仍是事实源，系统只读登记。
2. 每个模块移交时：先建库表与摄取，再提供 Markdown 导出/对账工具，对账通过后才在 AGENTS.md 中把该模块事实源改记为数据库。
3. 移交后 Markdown 成为导出物，携带生成时间与来源版本，不手工编辑。
4. 任何模块不得在未完成对账前双写漂移。

## 七、一期验收标准

1. `docker compose up -d` 后 `npm run db:migrate` 可重复执行且幂等；测试库上迁移、唯一约束、外键行为有单测覆盖。
2. 三个摄取脚本运行后：3 条任务定义、全部行情 CSV、当前正式回测（active）与历史报告（archived）在库中可查，路径与哈希与文件系统一致。
3. `record-task-run.mjs` 可完整登记一次运行（开始→结束，含产物与缺口）；同任务同目标日重复开始被拒绝。
4. `register-backtest.mjs` 可登记新 run 并激活为正式锚点，旧锚点自动降级，全程单事务。
5. 页面两个新视图可展示种子数据；旧纯前端构建与既有测试全部保持通过。
6. `git status` 无敏感产物：`.env.local`、`dist/`、数据库卷均被忽略；代码与错误信息不含凭据与绝对本机目录。
7. 全程未修改 `支撑/` 与根目录任何既有事实文件。

## 八、风险与依赖

| 风险/依赖 | 处理原则 |
|-----------|----------|
| Markdown 与 DB 双写漂移 | 一期只有新数据入库、旧事实源不动；二期移交带导出/对账工具（见第六节） |
| docker 不可用 | 退化为本机 Postgres + 同一 `DATABASE_URL`，README 两种写法都给出 |
| 历史回测指标缺失 | 登记留空，不从报告正文猜测 |
| 任务运行仍由 agent 人工触发 | 一期只提供登记 CLI，不做调度器；调度集成另行评审 |
