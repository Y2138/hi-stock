# Stock 策略演进系统 产品方案（现行）

> 2026-11-23 收口：本文只保留经当前代码、迁移和运行库核验的现行约束。内置回测已由迁移 `0110_内置回测功能下线.sql` 整体下线，`backtest_*` 表和回测工具/页面都不存在；回测在仓库脚本执行，结论整理成任务策略文档后经迁移写入。退役项见第十节。
>
> 事实优先级：当前代码与迁移文件 → PostgreSQL 当前策略正文（`strategy_document` / `strategy_state`）→ 本文。历史决策与实施过程以 Git 历史为准，不再保留在本文。

## 一、定位与用户问题

本机运行的单用户策略研究与执行记录工作台，桌面浏览器使用。当前策略、短线/长线池、行情与财务估值、持仓与成交归因、定时任务及结果、Agent 可复用记忆统一存入 PostgreSQL；页面负责查询与治理，Agent 负责需要理解上下文的业务写入。

| 场景 | 用户要回答的问题 | 系统输出 |
|------|------------------|----------|
| 打开系统 | 今天数据齐不齐、什么必须先处理、持仓什么状态 | 仪表盘：数据可信度、待处理异常、账户与持仓指标、任务健康、快捷操作 |
| 研究一只票 | 是否值得进池、当前结构如何 | Agent 评估后发起入池提案；页面从池、板块、搜索下钻日线行情 |
| 问事实 | 某只持仓什么成本、策略怎么规定、某次任务为什么失败 | AI 对话：工具直达库内事实，答案可追溯 |
| 复盘持仓 | 当前持仓如何、每次变更因何发生 | 持仓页：概览、变化时间线、个股 K 线 |
| 收盘后更新 | 今天怎么记、依据是什么 | Agent 复述事实与归因 → 结构化提案 → 确认入库 |
| 策略演进 | 当前最终策略是什么、最近为什么调整 | 当前策略正文 + 简要演进记录；待发布提案人工审核 diff |
| 自动化 | 任务跑没跑、失败怎么办 | 任务中心：状态、结果、启停、立即运行、失败重试、来源会话 |
| 换机器 | 怎么恢复全部历史 | 私有完整备份 + 固定资产包；恢复前人工确认 |

## 二、目标与非目标

### 2.1 目标

- 当前策略、短线/长线池、行情与估值、持仓与成交归因、定时任务及结果、Agent 可复用记忆全部入库可查。
- 行情以 PostgreSQL 为唯一事实源：页面、API、Agent 一律从 `market_bar` 等表读取，不读仓库文件。
- 服务端原生取数：`server/datasource/` 直连扶摇与 AKShare 底层公开接口，获取即落库；不经过 Python 或 CSV 中转。
- Agent 主导业务写入、页面负责查询与治理：标的入池、成交、作业定义与提示词、记忆均经领域 service；页面保留确认、策略发布、任务控制、模型设置和备份治理。
- 定时任务覆盖数据更新、策略扫描与 Agent 流程；每次 Agent 运行有独立 session，结果归具体运行，可回看与追问。
- 策略只保存当前最终正文与简要演进，不保存用户可见的历史正文；发布必须由真实用户批准。
- 私有完整备份与固定资产包分离：前者含本机业务数据，后者只含当前策略、评分基准、任务定义与提示词。

### 2.2 非目标

- 不做交易下单、券商连接、实时/盘中行情订阅。
- 不做多用户、权限体系、公网或局域网暴露、云同步。
- 不做 AI 自主买卖决定；对话内容不进入策略事实源。
- 不做 DB→Markdown 回写；不把回测代码、中间脚本或临时产物当数据库资产。
- 系统内不提供回测执行、回测页面或回测数据表（内置回测已下线）。

## 三、总体架构（现行）

```
浏览器 Vue 3 SPA（server 托管 web 构建产物）
   │ REST + SSE（Agent 流式）+ multipart（附件）
server/
   agent/       会话执行器、工具注册与校验、确认制/YOLO、系统提示词、模型接入（ai/、core/）
   datasource/  扶摇与 AKShare 通道、限流退避、获取即落库
   indicators/  指标计算与脏数据重算
   analysis/    板块温度、关键位、长线估值等库内计算
   modules/     accounts boards intraday-risk job-prompts macro market market-news memory
                notifications paper-trading plans pools positions selection strategy
                strategy-runtime ultra-short value-ranking weekly-review
   scheduler/   进程内调度、作业执行与结果入库
   volume/      私有完整备份与固定资产包（白名单导出、manifest 校验）
   http/、db/、migrations/、config.ts、system-settings*
   uploads/     对话附件（gitignored）
PostgreSQL      运行时唯一事实源
datavolume/     本机私有备份（gitignored）
bootstrap/      固定资产包（人工确认后入库）
```

- 服务只绑定 `127.0.0.1`，没有登录认证。
- 调度器随 server 进程运行，不做独立守护进程；停机缺口记为 missed，不伪装补跑成功。
- 前端构建产物由 server 托管，单一端口；开发期用 Vite dev server 代理 `/api`。

## 四、页面结构（现行）

左侧导航可在完整菜单与图标栏间切换；顶栏为全局状态条；右侧 Agent 工作区可收起、拖动并记忆宽度，收起不终止 session。旧悬浮抽屉已删除，`/chat` 只作兼容重定向。

| 页面 | 首要问题 | 主要内容 |
|------|----------|----------|
| 仪表盘 | 系统是否可信、什么必须先处理 | 异常聚合、持仓关键指标、近期关注与打板机会数量、数据与任务健康 |
| 当前策略 | 当前最终策略是什么、最近为什么调整 | 策略与指引当前正文、简要演进、待发布提案摘要与真人发布 |
| 短线池 / 长线池 | 研究对象与关注顺序 | 近期关注、板块视图、角色/分级/评分/股性/阶段/标签、行情下钻 |
| 持仓 | 持仓状态与每次变更原因 | 概览、持仓表、归因构成、变化时间线；写入转 Agent |
| 行情 | 区间对比与单标的日线结构 | 主标的加最多三个对比标的的归一化曲线、日线与期货日线 K 线、指标 |
| 市场结构 | 目标日情绪与资金结构 | 涨停、跌停、炸板、连板天梯、龙虎榜；涨停页展示收盘打板任务机会 |
| 市场消息 | 目标日有哪些可采信消息、覆盖到哪里 | 按日查看市场底盘、策略关联、异常扩展与覆盖缺口；消息卡片关联关注池单标的 |
| 期货 | 商品期货目录、主力连续与日线 | 合约目录、同步覆盖、日线与持仓量等明细 |
| 超短 | 竞价、打板、低吸的当日执行视图 | 竞价判定、排队与提醒、离场风控 |
| 任务中心 | 任务跑没跑、失败如何处理 | 运行状态、结果预览、来源会话、启停/立即运行/失败重试；定义与提示词只读 |
| 通知 | 邮件与站内通知的投递与历史 | 设置、投递记录与失败原因 |
| 数据与备份 | 数据获取与备份是否健康 | 数据源通道、覆盖缺口、私有备份与固定资产包的导出/恢复 |
| Agent 记忆 | 哪些已验证方法可复用 | 有效/待复核/已替代/已废弃列表，按类型、标签、验证时间筛选 |
| 设置 | 系统配置 | LLM 厂商/协议/Base URL/Key/模型目录与当前模型（key 不回显）、确认制/YOLO、通知 |

## 五、模块契约

### 5.1 行情与市场结构

- 扶摇通道：日线、指数/ETF/股票快照、涨停池、估值、财务、交易日历、期货；服务端校验业务信封 `code == 0`，限流退避、范围与代码校验，股票默认前复权。
- AKShare 通道：扶摇缺能力的数据（30 分钟线、期货主力连续、个股资金流），直连其底层公开 HTTP 接口，不经过 Python；失败显式留痕，不静默切换。
- 落库：`market_bar`（日/30m/期货日）、`market_instrument`、`market_board*`、`market_limit_event`、`market_dragon_tiger_entry`、`market_corporate_action`、`market_trading_day`、`valuation_snapshot`、`fundamental_snapshot` 等；同一标的同一日期幂等覆盖，缺口写入任务运行记录。
- 指标：`market_indicator_value` 按范围重算，缺口不推算；市场结构按交易日查询覆盖与缺口。

### 5.2 池与关注

- 研究对象只由短线池/长线池承载，没有独立自选清单。
- `pool_onboard` 单标的一次初始化：行情、财务估值、指标重算、股性/阶段/评分、官方行业校验，确认制一张卡，YOLO 直接写入。
- 同一标的只有一个当前角色；跨日切换原子结束旧行并保留历史。
- 近期关注由 `pool_attention_entry` 维护；系统信号与人工关注分来源独立保护。

### 5.3 AI 对话

- 分层：`agent/ai/` 统一厂商与模型，`agent/core/` 承载 loop，`agent/` 提供工具、确认、审计与 HTTP/SSE。
- 模型配置以 PostgreSQL 为唯一事实源；设置页维护厂商、协议、Base URL、Key、模型目录与默认模型；会话可独立选模型并持久化，Key 永不回显。
- 会话统一使用 `chat_session` / `chat_message` / 低频 `chat_session_event`；任务与交互共用会话执行器，任务结果归 `job_run_output`。
- 工具边界：只读工具按领域聚合（持仓/池/任务/竞价/策略/行情/指标/记忆/扶摇能力），排障用 `database_schema` 与 `database_query`（不接受原始 SQL）；写入工具按领域拆分并强制经领域 service；策略只创建待真人批准提案。
- 信任边界：工具参数按不可信输入在服务端再次校验；确认制未确认零写入，YOLO 仅跳过确认，校验、事务、保护表、审计和写锁不关闭；并发写用数据库锁与目标状态指纹防覆盖。
- 上下文达到模型预算约 80% 时压缩旧前缀并保留近期原文；`chat_message` 不因压缩删除。

### 5.4 当前策略

- PostgreSQL 保存当前最终正文（`strategy_document`）、整体状态（`strategy_state`）、评分基准与任务关联；不保存用户可见的历史正文。
- 策略清单哈希由 `strategy_document` 的 `code:sha256` 按 `injection_order,id` 拼接；改动策略正文的迁移必须同步刷新 `strategy_state.current_hash` 并 `change_seq + 1`，否则调度器拒绝执行 agent_flow 任务。
- 发布：Agent 只能创建提案，真实用户在页面批准；批准后原子更新受影响文档。

### 5.5 持仓

- `portfolio_position_change` 是变动事件源，`portfolio_position` 是当前投影；`market_bar` 只派生估值。
- 卖出固化成交前成本与本笔已实现盈亏；调整只修正数量或成本；备注只追加事件。
- 总资金/可用资金没有可对账来源，不展示、不估算；`portfolio_account_state` 只作风险门禁与组合净值台账。

### 5.6 定时任务

- `job_definition`（code、cron、job_type、enabled、config）+ `job_run`（queued/running/success/failed/partial/missed）；调度按 Asia/Shanghai 每 30 秒匹配 cron，扫描与执行槽独立。
- job_type 只有 `datasource`、`analysis`、`agent_flow`；不存在命令或脚本 Runner。
- agent_flow 固化绑定的 `job_prompt_revision` 与执行时策略状态，把任务说明作为首条用户消息，复用普通会话执行器与同一权限边界。
- 具体作业清单以 `job_definition` 与迁移为准，不在文档固定；启停、立即运行、失败重试是页面唯一控制入口。

### 5.7 Agent 记忆

- 只保存已验证、长期可复用的方法、模板、数据源经验与用户长期偏好；禁止密钥、业务数据副本、临时代码与一次性推测。
- 状态 active / review_required / superseded / deprecated；系统提示词只注入轻量索引，正文按需读取。

### 5.8 期货、超短与复盘通知

- 期货：`market_futures_contract`、`market_futures_daily_detail`、`market_futures_roll`、`futures_sync_coverage`、`futures_receipt_observation`；页面只读目录、覆盖与日线，不提供交易指令。
- 超短：竞价采样、盘中信号、关注池与离场风控按 `ultra-short` 模块与当日快照运行，不自动交易。
- 盘中风险与周复盘：`intraday_position_risk` / `intraday_position_signal`、`weekly_review_snapshot`；结果只作观察与复盘，不构成下单建议。
- 通知：站内通知与 SMTP 邮件分通道，设置与投递记录入库；失败留原因，不静默重试。

## 六、回测与策略验证边界（现行）

- 内置回测已由迁移 `0110_内置回测功能下线.sql` 下线：`backtest_event`、`backtest_equity_daily`、`backtest_run_comparison`、`backtest_run_source`、`backtest_run`、`backtest_input_chunk`、`backtest_input_set` 全部删除；服务端不再包含回测执行模块。
- 系统内没有回测工具、回测页面或回测数据表；Agent 不提供 `run_backtest` / `finalize_backtest` / 回测源码读取，也不保存回测源码。
- 回测在仓库 `scripts/` 中执行，结论整理成任务策略文档后经新增迁移写入；策略发布仍只由真实用户批准。
- 未经核验的研究结论不得写入策略正文；回测结论的证据等级、适用窗口与是否进入生产写在 `docs/回测结论/`。

## 七、数据事实源与数据边界

- PostgreSQL 是运行时唯一事实源；业务写入必须经领域 service，Agent 不获得通用 SQL 写权限。
- 本机运行数据（持仓、账户、流水、标的池、行情、聊天、任务结果、分析、回测结论）与私有备份不进 Git。
- 固定资产包只含当前策略正文、评分基准、定时任务定义、提示词及其版本；不含历史策略版本、行情、持仓与密钥。
- API Key 只存 PostgreSQL 设置表；查询接口只返回配置状态，密钥不进入日志、URL、错误、审计或固定资产包。
- `datavolume/` 是私有完整备份目录，含敏感数据，只允许本机或自有介质拷贝。

## 八、安全与边界

- 服务无认证，宿主端口必须绑定 `127.0.0.1`，不得暴露到局域网或公网。
- 迁移只向前：已应用文件不改名、不改内容；新变更新增迁移。
- 确认制与 YOLO 共用同一事务、写锁、状态指纹和审计；YOLO 不能发布策略。
- Agent 工具、Web 搜索与正文抓取按零信任处理：非法参数、未知字段、越权表/列和超大载荷直接拒绝。

## 九、验收基线

1. 策略、池、行情、持仓、任务与记忆可在页面查到，事实可追溯到数据库记录或版本。
2. 行情只从 `market_bar` 等表读取；抽取标的与外部原始行对账一致。
3. 断开外部 Python 与 CSV 后，datasource 作业仍能完成每日取数与落库，限流、退避和降级留痕。
4. 数据卷恢复后 manifest 行数与行情覆盖和库内一致，不一致必须列出差异。
5. 页面业务事实默认只读；入池、成交、作业定义/提示词、记忆写入只经 Agent 领域工具。
6. 确认制未确认零写入；YOLO 直接写入且页面明确警示；并发写与旧提案不得覆盖新状态。
7. 同一策略、阶段、目标日与输入指纹只执行一次评估；成功复用，失败或部分结果重试。
8. Agent 运行在模型调用前已有独立 session；断线可补过程，失败有日志，停机缺口记 missed。
9. 策略只能生成待发布提案；真实用户批准后多文档原子生效。
10. 持仓页只展示可从当前持仓、事件与最新行情验证的概览；缺行情时明确标记不完整。
11. 系统不存在 `backtest_*` 表、回测工具或回测页面；仓库脚本产出的结论只能经迁移进入策略正文。
12. 永久测试通过；仓库无密钥、附件、私有备份与运行数据；`git status` 干净可审计。

## 十一、待定方向

策略能力组合与渐进解耦（2026-11-11 PM 方向评审稿）尚未定稿，当前不改变现有行为、任务定义、接口和固定资产白名单。已收敛的有效结论：

- **走渐进抽取，不重写**：能力注册与策略组合复用 PostgreSQL、现有领域 service、评估器注册表、任务运行与模型设置；首期不建微服务、通用工作流编辑器、外部插件商店或任意脚本加载器。Agent 只能选择已注册能力并提出组合草案，不能注入脚本、修改 schema 或绕过 service 写库。
- **统一契约**：每个能力登记稳定编码、代码与 schema 版本、配置 schema、所需数据与权限、失败语义、幂等键、是否产生副作用；执行信封含运行 ID、事件/计划 ID、能力编码与版本、策略或手工来源、配置哈希、数据截至时间、输入指纹、覆盖与缺口。目标时间不能当实际数据时间。
- **结论与状态分离**：执行成功可以得到“无匹配”，缺数可以“无法判断”，能力报错是失败；无匹配不自动等于旧事件失效，依赖不兼容在启动前拒绝，不静默改默认参数。
- **共享对象**：发现记录、观察计划（价位须标用途、数值或区间、原始/复权口径、计算时点、证据与有效窗口）、观察结果（规则判定与模型解释分字段）、生命周期事件、评估结果；不同策略不强制统一收益窗口，状态机分发现、计划、机会、运行健康、渠道五层。
- **先抽三条边界**：策略产物与通用运行时之间（结果转换下沉各策略适配器，通用运行时只核验信封）；自选与观测之间（观测只消费生效计划，不从入池快照或 stage 反推规则）；观测判定与通知/复盘之间（规则先提交事件，投递与评估分别消费，投递失败可单独重试）。
- **并行迁移**：新适配器先影子运行、零副作用；逐条对照一致、可解释差异或不可重放（缺历史版本或点时数据就如实记不可重放，不倒填）；单策略切换、双路径并存、可回滚；证据齐全后才删旧分支。
- **数据边界不变**：能力代码随源码部署，组合与模型引用属配置，运行时仍以 PostgreSQL 为准；本阶段不改变导出白名单、密钥边界与迁移规则；原稿中的实施阶段和时间点不作为现行约束。
