## 一、总体判断

这是一份证据密度高、边界诚实的架构文档。它没有把“补数据”误当成“得到回测能力”，也没有把旧自由源码结果洗成正式证据。**核心架构决定（PostgreSQL 唯一事实源、双路径、标准路径不接收可执行源码、日频第一期、统一账本、冻结输入）均与本仓库既有约束一致**，可以直接作为实施基线。

两份文档的分工（缺口分析定义“需要什么”，架构规划定义“如何进入、执行、验收和交付”）清楚，交叉引用路径正确。

## 三、需要处理的问题

### 发现 1【重要·能力边界】内置 Agent 不能自主验证新规则，与预案预期存在落差

预案的原始诉求是“需要内置 agent 进行回测验证”。但架构 §4.1 明确：**标准路径只接受已注册规则，新的自由源码要进入标准路径，必须先形成仓库代码变更、通过测试、随应用发布**。自由源码路径保留，但“不可直接取得正式收益证据资格”。

这意味着：**Agent 能做的自主实验被限定为“选已注册规则 + 调参数 + 消融 + 解读”；任何全新规则（例如一个新的 ADX 复合过滤器写法）都不能由 Agent 自行编写并产出合格证据**，必须人工改代码。

这个取舍本身是合理的（可复现、可审计、防伪造收益），但它**直接改变了“内置 Agent 回测验证”这句话的含义**，属于用户需要明确知晓和确认的边界，建议在 §10.2 增加一条【待确认】【真实用户】项，而不是隐含在 §4.1 的实现说明里。若用户希望保留一定自主性，可考虑“Agent 起草候选规则 → 人工合入并标记为实验规则 → 再跑标准路径”的显式提升流程。

### 发现 2【事实·需更强修正】工作器默认值是 `true`，改 Compose 和文档不足以“默认关闭”

`isAgentBacktestWorkerEnabled()` 的回退值是 `true`（`server/backtest/agent-workspace.ts:118`：`booleanFlag(process.env.AGENT_BACKTEST_WORKER_ENABLED, true)`），`docker-compose.yml:34` 又显式设为 `"true"`，而 `docs/独立部署说明.md:98` 写“容器部署默认关闭”。

§8.2 提出“Compose 默认关闭并与部署说明保持一致”，但**如果只改 Compose 和文档、不改代码回退值，裸 Node 启动时工作器仍是开启的**。实施时必须同时把 `booleanFlag` 的回退值改为 `false`，否则“默认关闭”不成立。建议在 §8.2 明确写出这处代码变更。

### 发现 3【实现检查点】`execution_status` 的 CHECK 约束需显式扩展

现有枚举来自 `0009_analysis_backtest.sql:59`：`('legacy','queued','running','success','partial','failed')`。§4.9 的目标状态机新增了 `preparing / cancelled / rejected`，必须用新迁移 `ALTER TABLE ... DROP CONSTRAINT ... ADD CONSTRAINT ...` 扩展枚举，并保证旧行（含历史 `partial`）合法。

§5.2 只写了“阶段与进度”，未点名这处约束变更。建议在实施清单中显式列出，避免被当成纯加列而漏掉。

### 发现 4【数值风险】MACD/EMA 种子深度影响“基线一致”验收

生产指标读取 `max(bar_date) - INTERVAL '6 years'` 的日线，并**从该窗口第一根开始递归计算 EMA**（`server/indicators/service.ts:120-134`；`formulas.ts` 对齐 `ewm(adjust=false)`）。因此生产在任一历史的 `dif/dea/macd_hist` 都隐含 6 年预热。

若回测只冻结 3 年（甚至更短）输入，冷启动种子不同，**同一历史日期的 MACD 会与生产不同**，§7.1 的“基线一致”→“相同信号/温度/状态”就无法成立。

§4.5 已要求“记录初始化方法及收敛检查”，但**没有给出种子深度或收敛容差**。建议明确：右侧六条件涉及的递归指标，冻结窗口的预热深度应与生产一致（6 年）并剔除预热区间参与信号，或在验收里定义数值容差并单独披露。这是目前最可能在实施后“看似通过、实则不一致”的一处。

### 发现 5【口径·需标注】恢复条件比用户定义更严

用户已给定“情绪恢复 = 综合指数 MA20 斜率 ≥ 0”。架构 §4.8 的恢复规则在此基础上增加了“至少完整暂停一个交易日”和“当日无新触发”。这些是有价值的滞回设计，但**属于文档新增的设计选择，不是用户给的简单定义**。§10.2 已把恢复列为待确认，建议在 §4.8 该项旁注明“在用户定义之上增加的最短暂停与冲突优先”，让确认对象精确。

### 发现 6【歧义】基准数据的落点未指定

§5.3 数三十要求“同区间日线、收益类型与分红口径”，但没有指明复用 `market_bar` 的指数日线，还是新建基准表。目前指数日线覆盖很薄（579 个中多数仅 36 根），若基准依赖现有指数，需说明由哪条采集路径补到与策略同区间。建议在 §5.3 明确对象与回填来源。

### 发现 7【约束冲突】`formal + active` 全局唯一索引

`0001_init.sql:76` 建有 `backtest_run_single_active_formal` 唯一索引，全局只允许一条 `kind='formal' AND status='active'`。§4.9 说旧 `kind/status` 不赋予新资格，但没有说明**标准运行创建时用哪个 `kind`**。若沿用 `formal`，多条正式候选的正确性依赖它们都停留在非 `active` 状态，需在 §4.4/§5.2 明确标准运行在取得合格资格前的 `kind` 取值及锚点指派规则。

## 四、建议补充（非阻塞）

1. **数据回填的工作量被低估**。数一要求“按研究股票池和共同窗口回填个股 OHLCV、成交额”。当前股票日线只覆盖 565/5570 只，且生产扶摇单次取数有 3 年上限（`hithink.ts:158-172`）、“全市场十年日K”批量能力尚未接线。全市场 3 年回填是一个独立的采集与验收工程，建议在 §6 第一阶段把它列为独立的交付与容量验收项，而不是并入“数据预检与冻结”。
2. **固定资产白名单同步清单**。§5.4 方向正确。按 AGENTS.md，新增表必须同时更新导出、恢复清理顺序、校验、测试与部署文档；建议在实施清单里逐项列出（`portable.ts` 的 `PORTABLE_TABLES` / `RESET_STATEMENTS` + `migrate/migration-volume/volume-routes` 测试），避免只改一处。
3. **预案原文未同步**。`docs/系统策略优化方案预案.md` 仍是原始的 13 条速记，未标注“已被两份评审文档承接”。建议加一行状态说明，避免后续有人误把它当成最新口径。
4. **`input_chunk` 的 `bytea` 增长对私有备份的影响**已在 §5.4 提及，建议再补一句容量预估口径（5000 标的 × 3 年 ≈ 365 万行/输入集，按内容哈希去重后的典型与上限），便于维护者判断磁盘。

## 五、可以确认的默认决定

下列架构默认值与仓库约束一致，评审同意，无需再讨论：PostgreSQL 唯一事实源；标准路径不依赖 Docker Socket；不引入 Redis / 外部 Python Runner / 任意表达式 / 微服务；策略域仍只保存当前正文、运行不保存策略正文副本；新回测表全部排除固定资产；单实例并发 1、子进程隔离、预算超限拒绝而非裁样本；日频“收盘决策—次日开盘执行”并显式声明近似；模拟账本独立于实盘净值。

**第一期完成定义（§6）合理**：前六项通过 + 至少一套右侧基线与一个可执行变体在相同输入下产出可复核账本。若只有固定池/当前行业近似，技术可交付但结果保持研究资格——这个措辞准确，建议保留。
