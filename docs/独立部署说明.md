# Stock 独立部署说明

本文是部署 Agent 的执行契约。部署目标是：只用本 Git 仓库和 Docker Compose 启动 Stock；同步当前策略与定时任务固定资产，不同步个人业务数据。

## 一、部署边界

Git 可以包含：源码、迁移、产品与技术文档、测试，以及人工确认的当前固定资产包。

Git 不得包含：`.env.local`、任何 API Key、PostgreSQL 数据卷、`datavolume/` 私有备份、附件、持仓与账户、持仓流水、关注池、行情、任务运行结果、聊天或分析结果。当前允许提交的固定资产是：

- `bootstrap/stock_init_2026-08-21_135650.ndjson.gz`
- `bootstrap/stock_init_2026-08-21_135650.manifest.json`

该包只包含当前策略正文（组合总策略 + 各任务策略文档 + 指引）、策略使用的评分基准、定时任务定义、提示词及其版本，不包含历史策略版本，也不包含策略演进摘要或回测数据。恢复命令只允许用于没有 `schema_migrations` 的空数据库。

> **固定资产包版本**：策略体系已取消历史修订与演进摘要，可移植包格式现为 v7（包含当前策略运行时定义与任务关联，旧商品策略和任务已从导出白名单中排除）。恢复时按格式版本严格校验，旧格式包会被明确拒绝（提示“不支持的初始化包格式”）。当前已提交的 `bootstrap/` 包是旧版本，**不能**用于新电脑空库恢复；需要在真实用户确认后重新导出并提交一份 v7 包作为正式固定资产（届时同步更新本节的包名与 `.gitignore`/`.dockerignore` 白名单）。既有数据库不受影响：普通代码更新由启动迁移自动应用尚未执行的向前迁移。

## 二、目标电脑要求

- Docker Desktop，或支持 Compose v2 的 Docker Engine
- 可访问 npm、扶摇和所选 LLM 服务的网络
- 至少 2 GB 可用内存和足够的 PostgreSQL 持久化空间

无需在宿主机安装 Node.js、npm 或 PostgreSQL。服务无登录认证，只允许通过 `127.0.0.1` 访问，不得改成局域网或公网暴露。

## 三、首次部署

`git clone` 会自动下载源码和固定资产包，但不会自动修改目标电脑或写入数据库。以下步骤必须由目标电脑用户执行一次，因为它们涉及本机密码、空库确认和私有凭据。

```bash
git clone https://github.com/Y2138/hi-stock.git
cd hi-stock
cp .env.local.example .env.local
```

编辑 `.env.local`：至少把 `POSTGRES_PASSWORD` 改为仅含字母、数字、点、下划线、波浪线或连字符的本机专用密码，并让宿主机 `DATABASE_URL` 使用同一密码。不得在该文件填写扶摇或 LLM API Key。

先构建镜像并只启动数据库，再在应用容器中把固定资产恢复到空库：

```bash
docker compose --env-file .env.local build app
docker compose --env-file .env.local up -d postgres
docker compose --env-file .env.local run --rm app \
  npm run portable:restore -- bootstrap/stock_init_2026-08-21_135650.ndjson.gz
docker compose --env-file .env.local up -d app
```

不要在恢复前启动 `app`；应用启动会自动执行迁移，使数据库不再满足空库恢复条件。

首次部署的用户动作如下：

| 动作 | 是否必须 | 原因 |
|------|----------|------|
| 克隆仓库 | 是 | 获取源码与当前固定资产包 |
| 创建 `.env.local` 并修改数据库密码 | 是 | 本机私有配置不得由 Git 代填 |
| 执行一次固定资产空库恢复 | 是 | Git 只携带包，不自动写数据库 |
| 在设置页填写扶摇和 LLM Key | 使用对应功能时必须 | 密钥不随 Git 或固定资产同步 |
| 初始化行情与板块数据 | 按需 | 配置扶摇后手动运行数据任务，或等待定时任务；不会从旧电脑复制 |
| 初始化全市场历史日线（回测/研究需要时） | 按需 | 仅首次部署一次性引入：安装登录 `hithink-finance` CLI，`data init` 拉取批量导出，再 `npm run market:backfill -- --source duckdb`；之后日常更新由 `daily_data_update` 与 `market:fetch` 负责 |
| 复制持仓、流水或标的池 | 否 | 这些数据明确不跨电脑同步 |

历史回填的前复权开、高、低、收使用同一正斜率仿射变换，不能以可能为负的前复权收盘价比率缩放原始 OHLC。波段扫描只从已有至少 40 根日线的标的中选取代表样本；入选样本若存在行情或同日可信指标缺失，应从本轮自动扫描候选中剔除并列明原因，不得推断信号或删除人工标的池/真实持仓；全部候选不可评估时仍标记部分完成。

结论：新电脑需要用户执行一次固定资产空库恢复，并在本机配置密码和所需 API Key；持仓、持仓记录、标的池等业务数据没有同步步骤，也不会自动从旧电脑带入。

```bash

```

浏览器打开 <http://127.0.0.1:8787/>，确认当前策略和受控定时任务存在，只有空的“默认账户”，持仓、流水、标的池和行情为空。随后在“设置 → 数据源凭据”填写扶摇 API Key，在“设置 → AI 模型与厂商”配置 LLM；接口不会回显密钥正文。

## 五、更新现有部署

现有数据库不得再次恢复固定资产包。普通代码更新执行：

```bash
git pull --ff-only
docker compose --env-file .env.local build app
docker compose --env-file .env.local up -d app
```

服务启动时自动应用向前迁移。两台已运行实例之间不做自动双向同步；策略或定时任务固定资产更新时，应在源实例重新导出并人工审阅新 manifest，再为新电脑初始化。需要给已运行实例增加受控导入时，必须另行设计冲突检测与真实用户确认，不能复用空库恢复命令。

### 宿主机直接运行（非容器）

本机以宿主机 Node 直跑应用、数据库仍用容器时（`127.0.0.1:55432`），更新与重启步骤：

```bash
git pull --ff-only
npm ci
npm run db:migrate          # 先应用新增迁移；迁移只新增不改旧
kill <旧 PID>               # 先确认没有 queued/running 的 job_run
AGENT_BACKTEST_WORKER_ENABLED=true nohup npm run server >> .build/app.log 2>&1 &
```

- 启动后确认 `lsof -nP -iTCP:8787 -sTCP:LISTEN` 是新 PID，且 `curl -s http://127.0.0.1:8787/api/health` 返回 200；再调用一次 `POST /api/analysis/run` 确认服务层加载的是新代码。
- 日志写入 `.build/app.log`（已被 Git 忽略）；不要把日志或含凭据的输出提交进仓库。
- 当前没有 launchd/systemd 守护：进程退出或机器重启后不会自动拉起，需要按上面的命令人工启动。若要开机自启，另建 launchd plist 或 systemd unit，但本机配置（如 `AGENT_BACKTEST_WORKER_ENABLED`、`.env.local`）仍只能留在本机。

### 迁移版本与本机库记账（边界 1）

本机运行库在 2026-11-11 应用到了迁移 `0197`。其中 `0191`–`0194` 四个迁移文件当时仍在用户工作区未提交，只有 `0195`–`0197` 进入 Git。

- 换机器或重建库前，先确认这四个文件是否已经提交；缺文件时库版本会领先 Git，`schema_migrations` 与文件对不上，迁移器会拒绝继续。
- `0195`–`0197` 只新增影子表与索引，`strategy_signal_event`、`observation_plan`、`strategy_signal_outcome` 由影子开关 `HISTOCK_SHADOW_SIGNAL_EVENTS` 控制是否写入，默认关闭，不写自选、不产生通知或邮件。
- 补齐四个文件后，必须用只含 Git 内容的干净库从 0 迁移到最新版本，验证 `0195`–`0197` 不依赖未提交迁移；跑不通说明存在隐式依赖，需要补显式依赖或调整顺序。

**推送门禁（推送前必须做，不允许先推后补）**：

- 提交 `556d135` 曾在测试源码里写入 908 条导出中的真实 signal id、交易日与风险价，后续提交已移除代码里的样本，但该提交的历史仍保留那一段。清理后重放，再推送。
- 定时任务与测试不得再出现真实 signal id、真实交易日和真实价位；常规用例使用合成样本，真实回放只读被忽略的 `artifacts/`。
- 推送前执行 `npm run check:push`（默认扫描 `origin/main..HEAD`，也可传范围如 `npm run check:push -- ba93457..HEAD`）。命中即退出码 1，必须清理后再推。

**写入路由切换检查项（`signal_live_route`）**：

改路由、开关或任何写入路径之后，**只改数据库不算切完**。`tsx` 直接运行源码，运行中的进程仍是旧代码，必须按下述顺序确认：

1. 改 `signal_live_route`（`mode` 与 `generation`），记录切换前后的值。
2. **重启服务**：停止旧进程（`kill -TERM <pid>`，确认 8787 端口释放），再按部署方式启动；`curl -s http://127.0.0.1:8787/api/health` 返回 200。
3. **用一条真实写入验证**：确认新进程真的按新路由落了数据，而不是只看监听端口和健康检查。事件路径看 `strategy_signal_event` 是否出现新行，计划路径看 `observation_plan`。
4. 手动回放或补写的事件，必须在 `gaps` 里带 `replay:` 前缀标记，验收时按 id 单列，不能混进自然调度产物。
5. 回滚同样是一条 `UPDATE` 把 `mode` 切回 `legacy` 并把 `generation + 1`，然后重启进程；保留证据，不删数据。

### 两年结构反转原始价缺口修复


两年结构反转策略的合格行业成员需要目标日的未复权最低价。日常行情任务只对缺失的相关股票补取扶摇 `adjust=none` 日线，并写入既有股票日线的 `*_raw` 字段；不更改前复权价，不用前复权价推算原始价。若供应商缺数，任务记录缺口且扫描不得生成正式信号。修复过去某个交易日时，先在对应实例预览，再明确执行：

```bash
npm run market:raw-repair -- --date 2026-09-17
npm run market:raw-repair -- --date 2026-09-17 --apply
```

修复只补该目标日合格行业的缺失成员，不重放行情日更。任务中心“立即运行”默认使用当前目标日；若需复核历史目标日，明确指定日期后手动触发：

```bash
curl --fail-with-body -X POST http://127.0.0.1:8787/api/jobs/two_year_reversal_scan/trigger \
  -H 'Content-Type: application/json' -d '{"target_date":"2026-09-17"}'
```

仅在已完成普通代码更新、迁移且当前实例具备数据源凭据时运行，不对其他实例自动执行。

## 六、数据持久化与回滚

Compose 使用 `pgdata`、`uploads`、`backups` 三个本机 Docker 卷，分别保存数据库、附件和私有备份。删除容器不会删除这些卷；禁止执行 `docker compose down -v`，除非真实用户明确确认要永久删除本机全部数据。

完整数据卷会包含密钥、持仓和运行历史，只能留在本机 `backups` 卷或另行加密保存，不得复制进 Git。固定资产包不能替代完整私有备份。

### 本地研究回测

系统不提供内置回测台账、回测页面、Agent 回测工具或数据库回测表。历史回测执行已迁出应用，改为仓库根目录的本地研究脚本；脚本直接读取 PostgreSQL `market_bar`，结果只在终端或研究脚本指定的临时输出目录中生成，不写业务库。

全市场历史日线仍需在首次研究前按需一次性导入。常用入口包括：

```bash
npm run backtest:industry-trend
npm run backtest:relative-breakout
npm run backtest:structure-signals
npm run backtest:left-reversal
npm run backtest:trial-start
npm run backtest:jiangxi-copper-two-stage
```

其他仍保留的独立研究脚本及其参数见 `package.json` 和对应 `scripts/`。脚本结果统一按 `research_only` 使用，不构成生产收益证据。

本地回测结论进入系统的唯一链路是“本地回测 → 整理成任务策略文档 → 迁移写入”：

1. 在本地脚本中完成验证，形成可执行结论（不是完整回测报告，而是整理后的、能直接指导执行的规则）。
2. 新增或修改 `strategy_document` 中的任务策略文档（`role='task'`，`job_code` 指向对应定时任务），并重算 `strategy_state.current_hash`。
3. 对应任务提示词按需要调整，并把该任务加入 `job_workflow` 的必读门禁，确保任务运行时读取自己的策略正文。

内置 Agent 只读取系统内沉淀后的任务策略文档与任务工具结果；它不发起回测，也没有发布或改写策略的工具。策略正文的变更由迁移完成，页面和 Agent 均为只读。

## 八、飞书任务结论推送

设置页按“模型、Agent、数据源、消息推送、外观”分区显示，默认收起右侧 Agent 工作区；需要对话时仍可展开。在“消息推送”中配置接收群与任务范围，通知历史从“通知记录”进入独立页面。

在个人群和策略任务群分别添加飞书自定义机器人并开启签名校验。在 Stock“设置 → 消息推送”分别配置两组 Webhook 和签名密钥，分别发送测试消息并在“通知记录”确认投递后开启对应通道。若机器人设置关键词，需允许 `Stock`。

- Webhook 只接受 `https://open.feishu.cn/open-apis/bot/v2/hook/` 下的官方地址，禁止重定向，无需公网回调地址。
- 个人通道推送每日计划的真实持仓预案和盘中加减仓提醒；策略通道推送收盘打板、夜间板块、波段、竞价复核等其他 Agent 任务，可选择全部或指定任务。两个通道分别启停，数据同步任务不推送。
- 除盘后统一精选保留推荐理由与风险外，其他任务统一使用“任务名称与日期 → 简要说明（关注原因或核心条件，最多 120 字）→ 关注标的（名称、代码、所属板块、简短状态或持仓动作）→ 工作台结果编号”模板，整条消息最多 600 字符。名单过长时只省略完整条目并提示剩余数量；无关注标的时明确说明。每日计划只列本账户持仓，板块归属来自目标日有效的数据库关系，无可信归属时不猜测。数据缺口、T+1 验证、执行统计、评分和详细执行条件只保留在工作台，不进入飞书。
- 通知标题显示任务名称，与任务中心和订阅名称一致；盘中价位提醒显示“盘中加减仓提醒”。
- 盘前消息面探查覆盖当前关注池及全部账户持仓的去重标的，只读取代码、名称与行业，不读取账户成本或数量。完成检索但无新消息、剔除旧闻及正常时效说明不计为缺口；漏查标的由服务端自动列为缺口。成功或部分成功且有明确结论时，策略通道使用统一关注模板，保留数据库记录的当天整体偏向；不通知覆盖状态或缺口数量。失败或无结论不推送。
- 消息面整体预估按重要性、影响强度与范围、时效持续性、来源可信度和预期消化程度综合判断，最终方向为 `mixed 偏多` 或 `mixed 偏空`，市场消息页和飞书摘要同步展示。正文保留主导因素、反向风险和翻转条件；证据不足时明确说明。盘前判断针对当天，盘中手动运行针对剩余时段，休市日注明下一交易日暂定偏向。
- 任务结果与待发送通知在同一事务保存，后台约每五秒检查一次。通知失败独立重试，不重新运行 Agent 任务。不同任务的结果不会互相取消；同一任务、同一账户、同一目标日期的新结果会阻止旧通知继续补发；不同账户互不取消。
- “预览任务结论”仅在本机展示指定任务的最新成功结果，不发送消息。连接测试不含业务数据。结论可能包含持仓信息，请限定接收群成员。
- “通知记录”按任务、状态筛选，每页二十条，正文按需读取；历史记录保留，不随设置页展开。失败记录可补发原结论。
- 临时故障最多尝试三次，两次自动重试分别至少间隔一分钟、五分钟。机器人关键词等配置错误可在飞书修正后补发；某一通道凭据变更只取消该通道旧队列，需等待该通道新的任务结果。
- 关闭任一消息通道或取消策略任务订阅会暂停相应待发送结果，连接测试不受影响。凭据变更、通知超过二十四小时或已有同任务同日期更新结果时停止发送。开启后不补推开启前的历史结果。
- 已开始的请求不能撤回；飞书已接收但本机未收到响应时，重试可能重复通知。“飞书已接收”不代表用户已读。
- 推送配置、订阅任务、密钥、结论及通知历史是本机私有数据，完整备份包含这些数据，Git 固定资产包不包含。新电脑恢复固定资产后推送关闭，需重新配置。
- 手机通知不附带不可达的 `127.0.0.1` 详情链接。完整结论回到 Stock 工作台按结果编号查看，不得为消息跳转暴露无认证服务。

收盘打板机会由“收盘打板机会扫描”在工作日 17:25（`Asia/Shanghai`）独立运行，依赖目标日收盘市场结构数据。结构化候选只进入市场结构涨停页和下一交易日竞价任务；每日计划不再扫描或展示池外打板机会。竞价仅接收前一开市日成功扫描的候选，不回退旧每日计划或过期候选。

## 九、任务级模型与板块机会筛选

`agent_flow` 定时任务可独立绑定模型。任务未指定模型时，在创建本次运行会话时继承系统当前模型；指定后，本次运行及其自动重试都固定使用该模型。数据同步和分析类任务不能指定模型。模型不存在、被停用、所属厂商被停用或缺少 API Key 时任务明确失败。

模型层失败区分三类：零 token 终止（请求发出后从未收到任何文本增量）、已出字但流中断、看门狗超时（600 秒内没有任何文本增量）。命中任一类且任务在白名单内时，立即切换到 `glm-5.3` 重跑同一份输入与提示词，**不再等 5 分钟重试同模型**；只降一次不级联，降级目标也失败则任务判失败，不产出空报告。首批白名单只开“板块机会筛选”；盘中实时任务（持仓盘中观察、超短离场/观察、超短竞价、首板、竞价研判）一律不降级；盘前任务在 09:15 后不降级。降级轮的报告与飞书摘要首行会标注原模型、目标模型、触发类别和时间，并写入任务缺口与运行指标，供周报统计。非模型层失败仍按原规则五分钟后重试一次。

“板块机会筛选”在工作日 18:40（`Asia/Shanghai`）执行，默认绑定 DeepSeek V4 Pro（`deepseek-v4-pro`），并启用上述降级兜底：DeepSeek V4 Pro 只用于这类长文本、可容忍延迟的非实时报告任务，不做系统默认模型、不进盘中链路；一周内同一任务降级两次及以上时在周报复核是否继续使用该模型。任务通过 `sector_trend_structure` 分析对完整 881 一级行业做左侧趋势结构扫描，三触发线（中期脱离、新低回升、急跌反转）只决定板块是否进入观察，不再决定优先级；前两线要求近 15 日止跌 K 线与量比 <1.5，新低回升线为纯口径，均附 20 个交易日观察窗口；失效位为结构位制（MA5/MA10/近20日前低取最近有效档，并给第二道追踪位）；板块优先级由服务端当日确认度分档决定（M1 上涨家数占比、M2 相对上证涨幅、M3 涨停家数含20cm、M4 量比、M5 收盘位置与单根脉冲扣分；总分≥6 为 A、3–5 为 B、≤2 为 C，C 档只记录不输出个股也不写关注池）；板块内输出补涨候选（分支 A 跌幅补涨 / 分支 B 止跌修复确认，每板块最多 2 只），ST 与退市风险股以证券简称为主排除。没有信号时允许输出“暂无符合条件机会”。筛选结果只把 A/B 档写入关注池：A/B 档板块观察按条件成立记录，C 档板块只保留在报告与工作台，不写关注池；个股候选一律“即将符合”并列明独立证据缺口。共享关注不因某个账户已有持仓而抑制，无合格标的时以空集合完成对账。完整报告保留在任务工作台；飞书消息按分档顺序列出本轮筛选结果，每个板块固定给出板块名称与代码、简要原因（触发线、形态、量能、增强标签和观察窗口）和板块内标的，本轮复核但不在当轮板块内的标的单独收口，整条消息最多 600 字符。

实际运行前，必须在“设置 → AI 模型与厂商”为 DeepSeek 厂商配置有效 API Key，并确认厂商与 DeepSeek V4 Pro 模型均已启用；降级目标 `glm-5.3` 也需处于启用状态并具备可用凭据，否则该轮模型失败时无法降级。任务模型绑定属于固定资产：导出时记录稳定的 `provider_key/model_key`，恢复时映射到目标实例的模型主键，不携带 API Key。

## 多账户持仓与任务

普通代码更新会向前应用 `0164_多账户持仓与账户级任务.sql`，把存量持仓、成交、收益基线、净值和持仓任务归入“默认账户”。迁移不复制策略正文、行情或关注池，也不要求重新恢复固定资产。

账户选择器位于持仓页和任务中心的账户任务视图，支持新建、改名和查看归档账户；有持仓或排队、运行中任务的账户不能归档，默认账户保留。每日计划任务共享定义及提示词，定时触发时为每个有效账户生成独立运行、Agent 会话和结果；手动触发需在请求中提供 `account_id`。竞价任务已取消持仓复核并改为全局单次执行，不再按账户拆分。行情同步、市场结构和策略入场扫描保持全局单次执行。盘中风险共享一次行情采样，再按账户独立分析；账户任务通知注明账户名称。

每日计划分为共享市场层与账户持仓层。市场数据或关注输入改变时，共享上下文重算；账户成本、数量或成交改变只影响对应账户的退出评估。共享关注池信号不会因一个账户买入而被消费，其他账户仍可独立观察。

盘中加减仓价位观察固定使用 `GLM-5.3-Flash`，每 60 秒以当日个股量价为主，结合行业、指数及每五分钟采集的当日涨跌停/炸板情绪总数，给出加仓、减仓区间与确认/取消条件。不向模型提供成本、旧止损、历史计划或策略正文。情绪冰点关注有止跌承接的反向加仓机会，承接未形成时等待。至少三次有效来源采样、有近期成交、来源时间不超过 90 秒且当前价处于区间时才可触发个人提醒；条件失效、方向变化或过期时取消未发旧提醒，相同方向小幅价位抖动去重。持仓页以一行摘要展示触发计数与观察状态，展开后可看两侧条件预案，系统不执行交易。情绪快照为本机运行数据，不进入固定资产。每轮判断另按采样时刻追加一条盘中判断历史，保留当轮动作、价区间、依据和当时最新价，供事后复盘与胜率评估；历史只增不改，最新判断仍覆盖保存在原表，两者都只进入私有完整备份。

厂商 API Key 与套餐需具备该模型权限。权限、鉴权、套餐额度或请求配置错误只提示一次并暂停对应账户分析；在设置页更新或重新保存模型/厂商配置后自动重试。仅在厂商侧开通权限时，也需重新保存本机配置或重启应用。临时错误至少五分钟后重试。供应商错误正文与凭据不进入日志；失败、空正文、无效 JSON 或截断均不覆盖已有判断。旧版纯风险记录不作为新版价位提醒展示。

账户名称、持仓、成交、收益、计划和通知属于本机运行数据，只进入完整私有备份。可移植固定资产只增加任务作用域字段，旧的同格式包恢复时自动补齐内置任务的账户作用域；目标电脑只建立空的默认账户。新账户没有可信现金数据时不推测总资产或净值回撤。

## 邮件任务通知

任务结果可以通过独立 SMTP 邮件通道发送到固定收件人，与飞书推送互不影响：飞书的配置、开关、订阅和凭据变更不影响邮件，关闭邮件也不影响飞书。默认发送“每周交易复盘”和“盘后统一标的精选”的完整报告，可在设置页多选其它 `agent_flow` 任务；一个任务结果最多一封邮件。主题为 `Stock｜任务名｜目标日`，正文为任务完整报告 Markdown，页脚注明结果编号、目标日与“AI 生成，不代表策略发布或交易执行”。

### QQ 邮箱 SMTP 配置

1. 登录 QQ 邮箱网页版，进入“设置 → 账户”，找到“POP3/IMAP/SMTP/Exchange/CardDAV/CalDAV 服务”，开启“POP3/SMTP 服务”或“IMAP/SMTP 服务”，按页面提示完成验证。
2. 按提示生成“授权码”。授权码只在生成时展示，可随时重置；重置后旧授权码立即失效，需在 Stock 重新保存。
3. 在 Stock 设置页“邮件通知”分区填写：主机 `smtp.qq.com`、端口 `465`、SSL（`smtp_secure=true`）、账号为完整 QQ 邮箱地址（如 `xxx@qq.com`）、密码为第 2 步生成的授权码（不是 QQ 登录密码）、发件人与账号一致，收件人白名单 1–20 个。
4. 保存后点击“发送测试邮件”，在目标邮箱确认收到；再等待默认任务完成或手动触发任务，核对主题、正文与页脚。
5. 也支持 587 STARTTLS（`smtp_secure=false`）。若 QQ 邮箱提示需要扫码验证或设置独立密码，先在网页版完成安全验证，再重新生成授权码。
6. 修改授权码或收件人后重新保存会取消本通道旧待发邮件，需等待新的任务结果；已发出的邮件不能撤回。
7. 首次发信可能进入垃圾箱；短时间内频繁发送测试邮件或补发可能触发 QQ 邮箱发送频率限制，请控制测试频率。

### 163 与企业 SMTP

- 163 邮箱：`smtp.163.com`，端口 465（SSL）或 587（STARTTLS）；同样使用客户端授权码。
- 企业/自建邮箱：按服务商提供的 465（SSL）或 587（STARTTLS）参数填写；587 必须走 STARTTLS 且不允许降级到明文。
- 只接受 465 与 587，禁止明文 25；系统不提供关闭 TLS 的选项。主机只填域名，不能带 `smtp://`、端口或路径。

### 配置与测试

- 设置页为邮件提供独立配置区，与飞书推送分别保存、分别启停；保存时校验主机、端口、TLS 方式、账号非空、发件人与收件人格式及收件人数量，非法输入直接拒绝，不进入队列。
- 密码只写不读：已保存时页面只显示“已配置”，留空保存表示保持原密码；更换或清除需要显式操作。接口、日志和投递记录都不会返回密码或授权码。
- 测试邮件只验证 SMTP 连通与认证，不读取任务结论，不含持仓数据；测试成功后再开启通道并保存任务范围。
- 任务范围为默认两个任务加可多选的其它 `agent_flow` 任务；数据同步、维护类任务不可选。只有成功结果，或允许部分覆盖的默认任务的部分完成结果才会入队。

### 投递失败重试与记录

- 结果与待发邮件在同一事务保存，独立 worker 约每五秒领取；失败最多尝试三次，分别至少间隔一分钟、五分钟。
- 超过一天、SMTP 配置或密码变更、结果被更新版取代时取消待发邮件；关闭启用后不再入队，重新开启不补推关闭期间的结果。
- 设置页“最近邮件投递”折叠区可查看最近投递（状态、尝试次数、时间与脱敏失败原因）并补发失败记录；补发需邮件通道已启用、任务仍在订阅范围，复用原结果与正文，仍受一天过期和凭据版本一致约束。
- 失败原因只保留可操作类别，不含密码、授权码或完整错误正文；SMTP 服务器已接收但本机未收到响应时，重试可能重复发送。

### 邮件内容范围

- 默认两个任务的完整报告全文发送，不截断、不改写成摘要；部分完成的结果只在允许部分覆盖的任务上发送，并保留正文中的数据缺口说明。
- 主题与页脚格式固定；结果编号用于回工作台核对完整结论。邮件不附本机 `127.0.0.1` 链接，也不为跳转暴露无认证端口。
- 正文可能包含持仓、交易与策略判断，收件人应限定为本人或明确知情的可信地址。

### 数据边界与换机重配

- 邮件配置、收件人、订阅范围、投递记录与正文属于本机私有数据，进入完整私有备份；可移植固定资产包不包含。新电脑只恢复固定资产包时邮件通道为空，需重新配置。
- 即使恢复完整私有备份带回了配置，换机后也应重新核对 SMTP 参数、重新生成或确认授权码并发送测试邮件；QQ、163 授权码与企业专属密码通常需要重新生成。
- 邮件主题与正文会经第三方邮箱服务商（QQ、163 或企业 SMTP）传输和留存。
- 本机在 `email_delivery` 保留待发正文与投递记录，不另存 SMTP 会话日志；投递记录与正文进入完整私有备份，可随业务清理策略归档。
- 投递正文长期保留，当前无自动清理；如担心体积，可后续增加归档上限。

### 常见失败

| 现象 | 排查 |
|---|---|
| 认证失败 | QQ 邮箱未开启 POP3/IMAP/SMTP 服务；把 QQ 登录密码误填为授权码；授权码已失效或被重置；需要扫码验证或独立密码；账号与发件人地址不一致。修正后重新保存并发送测试邮件。 |
| 端口不通或超时 | 465/587 被本机网络、公司防火墙或云安全组阻断；误填 25（已禁止）。改用 465 SSL 或 587 STARTTLS，并确认出网策略。 |
| 收不到邮件（可能进垃圾箱） | 检查垃圾邮件/广告邮件目录并把发件地址加入白名单；第三方邮箱服务商的反垃圾策略与发件域信誉不由本系统控制，系统不保证送达。 |
| 配置保存失败 | 主机带了协议或端口、端口不是 465/587、TLS 方式与端口不匹配、收件人超过 20 个或格式错误。按提示逐项修正。 |
| 待发邮件被取消 | 配置或密码已变更、结果被更新版取代、超过一天未发出或通道被关闭；等待新的任务结果或重新发送测试邮件确认。 |

邮件通道的队列、凭据版本与开关独立于“飞书任务结论推送”章节；排查邮件问题时不需要改飞书配置，反之亦然。
