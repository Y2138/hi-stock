## 一、实施原则

1. PostgreSQL 继续作为运行时唯一事实源。
2. 策略规则只来自当前 `strategy_document` 和代码内受控评估器。
3. 数据库只保存评估器编码，不保存模块路径、脚本或 SQL。
4. 现有垂直工具和任务在新链路验收前保持兼容。
5. 每个数据库变化使用新的只向前迁移。
6. 持仓、关注、信号和评估运行属于本机运行数据，不进入 Git 固定资产。
7. 策略定义、任务定义和评估器绑定属于固定资产，必须同步更新导出、恢复和校验。
8. 自动关注按策略归属，人工关注始终独立。
9. 兜底策略只能按显式配置执行，不得掩盖主策略缺口。
10. 每个阶段只引入本阶段实际使用的抽象；旧代码在完成切换后再删除。
11. 任何临时验证测试无独立价值时在验证后删除。
12. 每个阶段形成独立提交，禁止把多个不可独立验证的阶段混成一个提交。

## 五、阶段 1：策略运行时数据模型

### 5.1 目标

建立完整 PRD 所需的数据结构，但不改变现有工具、任务、持仓和每日计划行为。

### 5.2 数据库迁移

新增迁移，版本从当前 `0115` 之后顺序递增。

#### 5.2.1 `strategy_definition`

字段与约束：

- `code`：稳定策略编码；
- `name`；
- `strategy_type`；
- `strategy_document_code`；
- `status`；
- `allow_new_entry`；
- `entry_evaluator_code`；
- `exit_evaluator_code`；
- `fallback_strategy_code`；
- `exit_policy_mode`；
- `daily_plan_scope`；
- `attention_policy`；
- `runtime_version`；
- 创建和更新时间。

数据库约束覆盖：

- 新开仓策略必须有入场评估器；
- 兜底策略不得有入场评估器；
- 兜底策略不得继续引用兜底；
- 仅退出或退役策略不得允许新开仓；
- `daily_plan_scope` 仅接受受控值；
- 文档编码必须存在。

#### 5.2.2 `strategy_evaluation_run`

保存评估身份、状态、版本、输入指纹、覆盖、缺口、任务来源和复用来源。

#### 5.2.3 `strategy_entry_signal`

保存正式和接近入场信号。普通筛除项只保留运行级汇总，不逐条持久化。

#### 5.2.4 `strategy_position_evaluation`

保存主策略或兜底策略对当前持仓的结构化动作。

#### 5.2.5 `job_definition`

增加：

- `strategy_code`；
- `agent_role`。

约束普通策略任务最多绑定一个策略；组合聚合任务不能绑定单一策略。

### 5.3 初始策略定义

迁移中建立：

- `swing`；
- `two_year_reversal`；
- `legacy_right_side`；
- `legacy_trial_start`；
- `legacy_left_reversal`；
- `limit_up`；
- `discretionary`；
- `portfolio_fallback_exit`；
- 已正式进入任务体系的关注型和组合叠加策略。

所有 evaluator code 在本阶段只作为受控配置写入，不启用新执行链路。

### 5.4 服务与 API

新增只读 repo 和类型，提供：

- 策略定义列表；
- 单策略定义；
- 按每日计划范围查询策略；
- 按策略读取关联任务；
- 评估运行基础读取。

前端暂不切换。

### 5.5 固定资产

`strategy_definition` 和任务关联字段加入可移植固定资产；评估运行和结果表排除。

## 七、阶段 3：持仓策略归属

### 7.1 目标

让每笔持仓拥有稳定策略身份，并阻止跨策略加仓覆盖管理口径。

### 7.2 数据库迁移

为 `portfolio_position` 和 `portfolio_position_change` 增加：

- `strategy_code`；
- `strategy_runtime_version`；
- `entry_signal_id`；
- `fallback_strategy_code`；
- `exit_policy_mode`。

迁移期间保留 `entry_signal_type`。

### 7.3 存量回填

按 PRD 映射回填；空值或无法确认的持仓保留空策略并进入待归因，不自动回填 `discretionary`。

### 7.4 写入服务

修改持仓领域 service：

1. 新买入必须提供 `strategy_code`；
2. 正式信号买入可以关联 `entry_signal_id`；
3. 自主买入使用 `discretionary`；
4. 已有持仓加仓只能沿用当前策略；
5. 跨策略加仓返回明确业务错误；
6. 卖出继承持仓策略；
7. 清仓后重新建仓可选择新策略；
8. 修正策略使用窄权限写入和真实用户确认；
9. `entry_signal_type` 在兼容期由策略映射自动双写。

### 7.5 Agent 工具

更新：

- `portfolio_write`；
- `position_entry_signal_write`，逐步升级为策略归因修正；
- 输入校验和确认卡；
- 系统提示词中的买入字段说明。

### 7.6 API 与前端过渡

持仓接口先增加策略字段；持仓页只读展示管理策略和待归因状态，完整交互在阶段 8 完成。

## 八、阶段 4：入场结果与关注池按策略归属

### 8.1 目标

让入场评估器成为策略关注集合的唯一计算来源，消除任务来源重复。

### 8.2 数据库迁移

为 `pool_attention_entry` 增加：

- `source_type`；
- `strategy_code`；
- `source_evaluation_run_id`；
- `last_evaluated_at`；
- `data_date`；
- `stale_reason`。

调整唯一性：

- 策略来源：`instrument_id + strategy_code`；
- 人工来源：每个标的最多一条；
- `source_job` 保留为最近触发任务。

### 8.3 存量关注迁移

按任务和当前规则映射到策略：

- 每日计划的波段正式/接近关注映射到 `swing`；
- 两年结构反转映射到 `two_year_reversal`；
- 价值、板块及其他任务映射到各自策略定义；
- 人工关注保持 `source_type=manual`；
- 无法映射的自动来源不得猜测，迁移中显式结束或标记缺口。

### 8.4 对账服务

实现 `reconcileStrategyAttention`：

- 成功：完整集合对账；
- 部分：只更新已覆盖标的，未覆盖旧条目标记待复核；
- 失败/不可用：不改变集合；
- 持仓标的抑制自动关注；
- 买入后只消费对应策略自动关注；
- 人工和其他策略条目不受影响。

### 8.5 Agent 写入边界

`pool_attention_write` 过渡为只接收评估运行引用或由策略服务内部调用。Agent 不再手工拼装同一策略完整集合。

### 8.6 前端过渡

关注池 API 返回策略来源；现有页面先使用策略名称替代任务名称，完整聚合展示在阶段 8 完成。

## 十、阶段 6：评估运行幂等与任务复用

### 10.1 目标

让每日计划、专项任务和交互查询复用同一结构化评估运行。

### 10.2 `ensureStrategyEvaluation`

实现：

1. 计算策略、阶段、目标日、版本和输入指纹；
2. 事务内领取或复用运行；
3. 相同身份运行中时不重复执行；
4. 成功运行直接复用；
5. 部分/失败按重试规则处理；
6. 输入推进后生成新运行；
7. 持久化覆盖、缺口和结构化结果；
8. 返回 `executed/reused/waiting` 元信息。

### 10.3 输入指纹

只纳入能影响结论的稳定事实：

- 策略运行版本；
- 当前策略文档哈希；
- 评估器版本；
- 目标日和实际数据日；
- 必要数据同步运行或最新事实版本；
- 出场阶段的持仓数量、成本、开仓日和策略归属摘要。

不把任务编码、会话或输出文案纳入指纹。

### 10.4 Agent 工具

新增 `strategy_evaluation_query`：

- 单策略任务的策略编码由会话范围固定；
- 交互会话可以按显式策略查询；
- 返回是否新执行或复用；
- 不暴露任意 evaluator code 参数。

### 10.5 任务角色

逐个迁移 Agent 任务：

- `strategy_entry_report`；
- `strategy_exit_report`；
- `strategy_confirmation`；
- `portfolio_aggregator`。

完成门禁按角色和策略能力计算，删除对应任务的重复工具名硬编码。

### 10.6 验证

```bash
npm run typecheck
npx vitest run tests/server/scheduler.test.ts \
  tests/server/chat-tools.test.ts \
```

## 十一、阶段 7：每日计划统一编排

### 11.1 目标

每日计划自动发现入场策略、持仓策略和兜底策略，替代当前按工具和信号类型硬编码的统筹方式。

### 11.2 自动发现

入场策略：

```text
status=active
allow_new_entry=true
daily_plan_scope 包含 entry
```

出场策略：

```text
当前持仓出现的 strategy_code
+ 持仓显式 fallback_strategy_code
```

组合上下文：

```text
daily_plan_scope 包含 context
```

### 11.3 编排服务

实现 `queryDailyPlanStrategyContext`：

1. 锁定策略状态；
2. 读取市场和风险门禁；
3. 校验持仓归属；
4. 确保入场评估运行；
5. 按策略批量执行主出场评估；
6. 按配置执行兜底评估；
7. 完成关注集合对账；
8. 合并主策略、兜底和有效动作；
9. 汇总覆盖和缺口；
10. 返回每日计划唯一结构化上下文。

### 11.4 Agent 工具

新增 `daily_plan_strategy_query`；每日计划任务只需：

- 读取组合总策略及返回结果涉及的策略文档；
- 调用一次统筹工具；
- 调用一次 `daily_plan_write`；
- 不逐个调用垂直工具；
- 不手工计算关注集合；
- 不自行决定兜底。

### 11.5 结构化预案

扩展 `daily_plan_playbook` 或关联结果，使每笔动作保存：

- 策略；
- 运行版本；
- 主评估运行；
- 兜底评估运行；
- 主动作；
- 兜底动作；
- 有效动作；
- 数据日和缺口。

### 11.6 并行运行与切换

至少使用固定历史样本和当前测试库执行新旧链路对比：

- 入场信号；
- 接近候选；
- 关注变更；
- 全部持仓动作；
- 打板观察；
- 覆盖状态；
- 缺口。

完成一致性确认后，切换每日计划提示词、工具包和完成门禁。旧上下文保留一个兼容周期后再删除。

## 十六、完成定义

完整 PRD 视为实现完成，必须同时满足：

- 策略、入场、出场、关注、持仓和任务存在可查询关联；
- 每日计划自动发现并覆盖全部相关策略；
- 关注池按策略唯一归属并正确对账；
- 持仓按策略选择专属和兜底出场；

- 专项任务和每日计划复用评估运行；
- 不存在任意策略—任务多对多维护入口；
- 前端完整展示策略关系、来源、动作和缺口；
- 存量业务结果完成一致性验证；
- 兼容路径和废弃分支完成清理；
- 固定资产、部署文档和全量测试全部通过。
