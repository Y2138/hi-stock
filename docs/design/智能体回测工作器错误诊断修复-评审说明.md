# 智能体回测工作器错误诊断修复评审说明

> 文档状态：已确认并完成验收  
> 评审对象：研发、测试、安全、运维  
> 事实来源：近期 `backtest_run` 记录、隔离工作器真实代码、同资源边界标准探针  
> 最后更新：2026-08-21

## 一、评审摘要

- **目标：** 修复复杂回测失败时诊断信息不足、智能体把策略运行错误误判为工作器容量退化的问题，并建立可验证的大数据回测容量基线。
- **核心方案：** 把工作器错误细分为策略运行、结果契约、超时、资源终止、容器启动和输入上限，并向智能体返回固定安全错误码、执行阶段和源码位置；为覆盖 50 万行硬契约，将输入上限调整为 128 MiB、容器内存调整为 1 GiB、超时调整为 60 秒。
- **主要影响：** 修改隔离工作器错误信封、服务端错误映射、`run_backtest` 工具说明和既有回测测试；不改变回测 SDK、不保存临时代码、原始异常正文或调用栈。
- **确认结论：** 50 万行是硬性验收上限；智能体可依据安全错误码自动纠正临时源码并最多重试一次。

## 二、背景与目标

### 2.1 背景

【事实】运行 #39、#40、#41 分别在 10.882 万、10.882 万和 4.4669 万根日线下失败，耗时约 3.18 秒、1.86 秒和 1.32 秒，数据库错误均为“回测策略运行失败”。这些运行既没有触发 20 秒超时，也没有形成“未产生有效结果”或 OOM 类错误。

【事实】在当前时点使用相同 `node:22-alpine` 镜像、256 MiB 内存、1 CPU、20 秒上限和同一工作器入口执行受控线性策略，4.466 万根与 10.8864 万根日线均成功，容器耗时约 1.7 秒和 1.1 秒，退出码为 0，`OOMKilled=false`。

因此，**现有证据不支持“工作器数据负载上限持续下降”的结论**。更符合证据的解释是：复杂临时策略在运行期抛出了异常，而当前安全错误映射把异常类型和执行阶段统一折叠为“回测策略运行失败”，导致智能体错误地继续减标的、减变体并把问题归因给环境。

### 2.2 目标与验收

| 目标 | 可观察的验收信号 | 来源 |
|---|---|---|
| 正确区分策略错误与容量错误 | `run_backtest` 返回固定错误类别、阶段和可用源码位置，不再只返回通用文本 | 【事实】现有错误映射过度折叠 |
| 保持临时代码安全边界 | 数据库、消息、事件、审计和日志中均不存在源码正文、原始异常正文或策略自定义异常内容 | 【事实】现有安全契约 |
| 覆盖契约容量上限 | 恰好 50 万根日线的线性多标的策略在资源边界内完成，且 `OOMKilled=false` | 【用户确认】50 万行是硬性验收上限 |
| 防止无效重试 | 策略错误时智能体优先修源码；只有资源、超时或输入上限错误才能判断容量不足 | 【方案】工具提示与系统提示约束 |

### 2.3 范围边界

**范围内**

- 工作器错误分类、执行阶段和安全错误码。
- Docker 进程退出码、超时和资源终止的区分。
- 智能体收到失败后的重试规则。
- 恰好 50 万根日线的容量基准与回归验收。

**范围外**

- 不恢复或持久化已经删除的 #39～#41 临时代码；其源码按既有安全设计不可恢复。
- 不修改策略逻辑、历史回测结论或当前策略正文。
- 不引入新的队列、分布式计算或外部回测引擎。

## 三、现状与约束

| 事实或约束 | 证据位置 | 对方案的影响 |
|---|---|---|
| 运行期异常只保留 `kind` 和可选位置，服务端其余信息统一映射为通用错误 | `worker-runner.mjs`、`formatAgentBacktestWorkerError` | 必须增加固定安全错误码和执行阶段 |
| Docker stdout/stderr 被直接丢弃，非结果信封失败也丢失退出原因 | `executeContainer` | 需保留退出码和内部状态，但不得持久化原始输出 |
| 修复前容器限制为 256 MiB、1 CPU、20 秒，且工作器串行执行 | `agent-workspace.ts`、`agent-contract.ts` | 保留串行与 1 CPU；为硬验收调整为 1 GiB、60 秒 |
| 修复前输入行上限为 50 万，但 JSON 输入上限仅 32 MiB | `AGENT_BACKTEST_MAX_ROWS`、`AGENT_BACKTEST_INPUT_LIMIT` | 将输入上限调整为 128 MiB，并以真实对象格式验收 50 万行 |
| 临时代码正文只能存在于本次工具参数内存和一次性工作区 | 技术设计 T35/T38、`redaction.ts` | 诊断不得返回原始错误正文或持久化源码 |
| 工具说明未规定如何解释不同失败类型 | `tools.ts`、`prompt.ts` | 需补充失败后的决策规则，阻止错误归因和盲目重试 |

## 四、方案总览

### 4.1 核心思路

- **先让失败可判定：** 工作器在读取输入、建立行情索引、加载策略、执行策略、校验结果和写出结果之间维护明确阶段；失败信封只返回固定错误码、阶段和源码行列。
- **区分策略与进程故障：** 服务端保留 Docker 退出码并映射超时、被终止、启动失败和异常退出；仍不保存 stdout/stderr。
- **让智能体按错误类别行动：** `strategy_*` 只允许修正源码后重试；`result_contract_*` 修正返回值；只有 `worker_timeout`、`worker_resource_killed`、`input_limit` 或 `container_start_failed` 才能归因到容量或环境。
- **容量按硬契约配置：** 保持 1 CPU 和串行执行，将输入、内存和时间边界调整为 128 MiB、1 GiB、60 秒，并以恰好 50 万行真实对象格式探针作为验收门槛。

### 4.2 影响面

| 影响面 | 变化 | 不变边界 |
|---|---|---|
| 工作器结果信封 | 增加安全的 `phase`、`code`、`location` | 不返回原始 `message`、stack 或源码 |
| 服务端执行器 | 记录退出码并映射固定进程错误 | 仍为无网、只读、非 root、资源受限容器 |
| 回测运行记录 | 继续使用现有 `error_message` 保存稳定中文错误，不新增业务事实 | 历史运行不回写、不猜测旧错误原因 |
| 智能体工具与提示词 | 明确失败分类和最多一次针对性修正重试 | 不允许通过反复缩小样本掩盖策略错误 |
| 回测 SDK | 无变化 | 现有策略函数签名和数据结构兼容 |

## 五、关键决策

| 决策问题 | 选择 | 备选方案 | 选择理由 | 影响与代价 |
|---|---|---|---|---|
| 是否覆盖 50 万行 | 【已确认】输入 128 MiB、内存 1 GiB、超时 60 秒，保留 1 CPU | 维持原 32 MiB、256 MiB、20 秒 | 用户明确要求覆盖现有 50 万行契约上限；真实探针已通过 | 单次工作器可使用更高内存和更长时间，但仍串行执行 |
| 是否允许智能体自动纠错 | 【已确认】依据安全错误码修正临时源码，最多重试一次 | 所有失败均停止等待人工处理 | 策略错误可在不泄露源码的前提下由智能体当轮修正 | 同一错误重复即停止，环境错误不伪装修源码解决 |
| 是否返回原始异常 | 【方案】只返回固定类型、阶段和位置 | 返回完整 message/stack | 保持临时代码与策略自定义异常不进入持久层 | 某些错误只能定位到类别，不能暴露具体值 |
| 是否新增数据库字段 | 【方案】不新增；使用稳定的 `error_message` 代码前缀 | 新增 `worker_diagnostic jsonb` | 当前目标是让智能体当轮纠错，避免不必要迁移 | 后续做容量趋势看板时可能再结构化 |
| 是否保留失败源码以便复跑 | 【方案】继续立即删除 | 加密或短期持久化源码 | 现有安全边界明确禁止源码进入数据库、消息、审计和备份 | 历史 #39～#41 无法原样重放，必须重新生成 |

## 六、详细设计

### 6.1 错误契约

| 当前 | 变更后示例 | 智能体动作 |
|---|---|---|
| `回测策略运行失败` | `[STRATEGY_REFERENCE_ERROR] 阶段=执行策略，位置=第 83 行第 17 列` | 修正未定义变量后最多重试一次 |
| `回测策略运行失败` | `[STRATEGY_TYPE_ERROR] 阶段=执行策略，位置=第 126 行第 9 列` | 检查对象、数组或函数调用形态 |
| `回测策略运行失败` | `[STRATEGY_STACK_OVERFLOW] 阶段=执行策略` | 删除递归或大数组展开，不判断为环境退化 |
| `回测工作器未产生有效结果` | `[WORKER_RESOURCE_KILLED] 退出码=137` | 进入容量诊断，不重写策略结论 |
| `回测工作器未产生有效结果` | `[CONTAINER_START_FAILED] 退出码=125` | 检查 Docker 和镜像状态 |
| `回测工作器超过限制` | `[WORKER_TIMEOUT] 上限=60000ms` | 判断算法复杂度或再评估时间预算 |

工作器仅按错误对象类型和受控正则映射代码，例如 `ReferenceError`、`TypeError`、栈溢出、非法数组长度；不得透传异常正文。工作器版本升级为 `agent-backtest-worker-v2`，SDK 仍保持 `stock-backtest-sdk-v1`。

### 6.2 智能体重试规则

1. `STRATEGY_*`：问题属于临时代码；结合阶段和位置修正一次。若同一错误码与位置重复，停止并报告源码问题。
2. `RESULT_CONTRACT_*`：只修正返回契约，不缩小行情范围。
3. `WORKER_TIMEOUT`：先检查明显的平方级循环、大数组展开和重复指标计算；只有算法已线性化仍超时，才提出资源调整。
4. `WORKER_RESOURCE_KILLED`、`INPUT_LIMIT`、`CONTAINER_*`：才进入环境或容量排查。
5. 禁止仅依据 bar 数、源码字节数或前一次成功规模推断环境正在恶化。

## 八、验收与验证结果

| 验收行为 | 计划验证方式 | 观察信号 | 风险或缺口 |
|---|---|---|---|
| 未定义变量的策略失败 | 在既有 `backtests.test.ts` 增加临时策略夹具 | 返回 `STRATEGY_REFERENCE_ERROR` 和源码位置，正文不含策略自定义消息 | 无 |
| 大数组展开或递归失败 | 增加栈溢出夹具 | 返回 `STRATEGY_STACK_OVERFLOW`，不返回 raw stack | 不同 Node 小版本错误文本需用受控兼容映射 |
| 结果契约失败 | 复用现有契约测试 | 继续返回具体契约诊断，行为不回退 | 无 |
| 50 万行输入容量 | 真实 Docker 下生成 100 个代码、每个 5000 根、合计 50 万根日线并运行线性策略 | 54.15 MiB 输入，1 GiB、1 CPU、60 秒边界下 14.07 秒成功，`OOMKilled=false`，处理 500000 根 | 证明契约输入链路与线性策略，不承诺任意复杂度算法均在 60 秒内完成 |
| 真实策略错误 | 在同一 Docker 边界运行未定义变量策略 | 1.84 秒返回 `STRATEGY_REFERENCE_ERROR`，`OOMKilled=false`，未包含变量名、原始异常正文或调用栈 | 原 #39 源码已删除，不能逐字复现 |
| 安全脱敏 | 复用源码持久化哨兵测试，并检查真实工作器错误信封 | 运行记录不存在源码；错误信封不存在原始异常正文和调用栈，因此消息、事件、审计和日志没有可持久化的原文输入 | 无 |

## 九、风险与回退

| 风险 | 触发条件 | 缓解措施 | 回退或恢复 |
|---|---|---|---|
| 错误分类泄露策略内容 | 透传原始 message 或 stack | 只允许固定枚举、阶段和数字位置 | 退回现有通用错误映射 |
| 过度依赖错误文本 | Node 升级导致原生错误文案变化 | 优先按错误构造器分类，文本仅匹配少数固定资源错误 | 未识别时降级为 `STRATEGY_RUNTIME_ERROR` |
| 诊断修复后复杂算法仍超时 | 策略存在平方级循环或大量中间数组 | 先线性化算法，再基于明确 `WORKER_TIMEOUT` 决定资源预算 | 保持串行工作器并中止该运行 |
| 50 万行真实对象将来超过 128 MiB | 行字段扩展或单行内容显著增长 | 先压缩不必要字段；只有真实超限后再评估流式输入 | 当前验收样本为 54.15 MiB，仍有明确余量 |

## 十、待确认事项

无。用户已确认 50 万行硬性验收和智能体最多一次自动纠错；安全边界保持不变。

## 十一、评审结论

- 结论：通过
- 已确认决策：50 万行是硬性契约上限；智能体可依据安全错误码自动纠错并最多重试一次；临时代码、原始异常正文和调用栈继续禁止持久化。
- 验收结果：类型检查、网页类型检查和既有回测测试通过；真实 50 万行 Docker 探针 14.07 秒完成，`OOMKilled=false`；真实错误探针正确脱敏。
